## What the display cluster had in common

`179158`, `179164`, `179088` and `179157` were one defect in four
surfaces: the artifact the owner is told to trust described something other
than what they were authorizing. Calldata summarised but never shown; a
decoded message whose escaping cannot distinguish a real override from its own
escape; typed-data members displayed and not signed; a policy diff rendering a
widening as a removal.

Two of the fixes introduce bounds, and both state what they elide — calldata
past 512 bytes reports the head, the exact length, and a keccak of all of it;
the balance list names how many tokens were omitted. A cap that reads as the
complete thing would have been a new instance of the same bug.

⁴ Splits three ways. The policy-bypass claim is the documented cancellation
exception in threat-model invariant 4 — verified against the code, which builds
exactly the fixed envelope the model describes. The human-presence claim is
invalid: invariant 6 gates *exceptional review*, and cancellation is not that.
The legal-acceptance claim is genuine and fixed — the two CLI cancel routes
skipped a gate `wallet_attempt_cancel` applies. Re-rated medium → low.

⁵ Not fixed, because there is nothing portable to fix it with: Windows offers
no directory handle `sync_all` accepts, and the alternative needs privileges
this process does not have. `MoveFileEx` means the file is never torn, so the
residual is losing the most recent save to a power cut, which is now stated in
the code rather than left looking like an oversight.

`179157` took two commits. The first covered chains, targets, and tokens and
claimed it had covered every level; approval spenders, the tokens nested under
them, and transfer recipients resolve through `exact_or_wildcard` too. V12
accepts one comment per finding, so the correction is in `2e55ece` rather than
on the finding.

## Beyond the audit

Work in the same area that did not come from a V12 finding, recorded here
because it changes what several of the verdicts above depend on:

- **Agent-supplied metadata is untrusted, and gated.** Token names and network
  profiles join address-book entries in requiring a terminal confirmation *and*
  an OS presence check before they are stored. `wallet_add_network` became
  `wallet_propose_network` and writes nothing. A boundary tripwire fails the
  build if `src/mcp.rs` names a store write helper outside its tests.
- **The RPC is documented as a trust assumption**, with `eth_getProof` and a
  local `revm` execution priced as the two ways out and the latency each costs.
- **The database key entry is `org.ekubo.wallet.db`**, named for what it opens
  rather than for policies alone.

¹ Filed low, re-rated **high**. See below.

² Revisions are monotonic per wallet and only reset when the row is deleted,
which now happens only inside `PolicyStore::purge` — the same transaction that
deletes the proposal. Making revision N reappear beside a live proposal
therefore requires restoring an older `policies.db`, which the threat model
already records as accepted: *"Restore older valid encrypted database — Not
detected; may restore an older policy or signed transaction."* One latent
hazard left deliberately: the now-unused `PolicyStore::delete` removes a policy
without its proposal, so wiring it back into removal would make the ABA real.

³ `assert_schema_current` runs in `tool_gate` rather than inside each write
transaction, which is a genuine TOCTOU shape — but with the schema collapsed to
a single version no build writes any other, and changing `schema_metadata`
requires the SQLCipher key. The window is unreachable. If a migration is ever
reintroduced, the version must be re-asserted inside the writing transaction.

## Findings whose severity changed

**179056 — low → high.** Correct as filed against `a58dfc2`, where the
sanctioned path also trusted contract-supplied metadata, so a legacy file was
no worse than `symbol()`. The post-audit commits inverted that: `tokens` became
the sole authority on what a reviewer reads, behind an owner-only quarantine.
That made `import_legacy_database` the only unauthenticated writer to the
trusted table, and the threat model puts the filesystem outside the boundary.

**179031 — medium → low.** Both encodings expand rather than contract, so the
decode allocates less than the URL string already resident. The ordering is
still worth fixing; the memory amplification described is not there.

**179045 — medium → info.** Documents a resolved state, not a live defect.

## Notable corrections to the report

**179057 is invalid.** The premise that `OFFSET n` costs O(n) does not hold:
both `list` statements order by `chain_id, address`, which is the table's
primary key, so SQLite walks that index and an offset past the end costs one
scan — less than the `SELECT COUNT(*)` the same handler already issues.

**179050 is understated** and still open. `wallet_add_network` returns the
probe target's response body verbatim to the caller, so it is an SSRF *read*
primitive rather than a blind probe. Separately, `docs/threat-model.md:171-174`
claims OS owner authentication runs before the first request to a proposed
URL. It does not, and the claim contradicts the same document's invariant 6,
which states network changes are deliberately *not* OS-authenticated. The doc
needs correcting with the fix.

## Verified and queued

Confirmed live against current `main`, with the fix identified, not yet
written. Recorded here so the analysis is not lost.

**Truthfulness of what the owner reads before signing.** `179158` — the
approval review shows a selector and a calldata *length*, never the bytes; the
"reads as" line is a descriptor summary that can differ from them, and its own
fallback tells the reviewer to "verify the target and selector directly" when
the bytes are on no screen. `179164` — a message that is valid UTF-8 is shown
decoded only; the hex goes out solely in the non-UTF-8 branch, and the escaping
is not injective, so literal `\u{202e}` and a real U+202E render identically.
`179088` — the gated typed-data document is the raw submitted JSON, while the
hash covers only fields declared for `primaryType`, so a reassuring key present
in `message` but absent from `types` is displayed and not signed. `179157` —
the policy diff shows a removed key as a restriction when a surviving `*` entry
means authority actually *widens*; `exact_or_wildcard` falls back at chain,
target, spender, token, and recipient level, and `diff_policies` compares key
sets independently.

**Cancellation pricing.** `177936`, `177946`, `179216` are one defect with
three faces: `attempt_cancellation` treats a caller-supplied record as
authoritative for pricing and `store_cancellation` accepts whatever it is
handed, with no compare-and-swap on the incumbent. Re-reading the row under the
lock plus a CAS on the newest hash closes all three; the attempt-budget
fallback (an attempt is consumed even when the broadcast fails, and the ceiling
of 8 is permanent) is the separate piece.

**Config durability.** `179108` — `Path::exists()` is false for *every* stat
error, not just absence, so an unreadable `config.json` loads as defaults and
the next `update()` atomically overwrites the real one, destroying the wallet
roster and every configured RPC. This is the most serious item left in that
cluster.

**Others confirmed live:** `179132`, `179246`, `179030`, `179136`, `179117`,
`177832`/`179103`/`179249` (one fix family: cap the config read and bound
network and alias counts), `179115`/`177855`/`177856` (private-mode hardening),
`177851`/`178990` (make `save` non-public so the lock cannot be bypassed),
`177928`, `177948`, `179139`, `179217`, plus the resource-bound and signature-queue
clusters not yet swept.

`179076` splits: the policy-bypass claim is the documented cancellation
exception in threat-model invariant 4 and is **accepted**; the human-presence
claim is **invalid** (invariant 6 gates exceptional review, not cancellation);
but the CLI cancel paths genuinely skip the legal-acceptance gate that
`mcp.rs` and `run_approve` both apply — a live, low-severity inconsistency.

## Closing the run

`v12_findings(runUid: 6161, validity: "unreviewed")` returns zero. Every one of
the 104 findings carries a triage comment naming its commit or its rationale.

Two dispositions worth restating, because they are decisions rather than work
left undone.

**The stdio transport.** `179062` and `179194` are correct that every list and
document limit in this server runs after `serde_json` has materialized the
frame. That cannot be fixed in a tool handler: the frame is read and
deserialized by the rmcp stdio layer before any handler is entered. The fix is
a bounded reader at that boundary — a dependency-level change, recorded here so
it is known work rather than an open question. The residual is small: the peer
is one local client, and a killed process loses queued work rather than
integrity, since nothing on that path is signed or committed.

**Per-caller quotas.** `179066` and several sibling findings assume a caller
that can be quotaed separately from the process. There is not one. A single
stdio process serves a single client, so "untrusted caller" and "the only
caller" are the same party, and a per-caller limit would be a limit on the
server itself. Where flooding is possible it fails safe: a full queue refuses
new requests rather than dropping or auto-approving existing ones.
