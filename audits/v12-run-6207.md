## The three that mattered most

**`183231`** is the one to read twice. `remove` tested
`config.wallet(id).is_ok()` to decide whether the metadata row had survived a
failed update, and that call reports an unreadable configuration exactly as it
reports an absent row. A read error therefore looked like "already removed",
fell through to `keys.delete`, and destroyed the only copy of a key whose
wallet was still listed. Deleting a credential now needs positive proof no row
bears the name.

**`183975`** made the canonical-form check and the default-deny nearly cancel
out. A non-canonical call was reported as a plain non-match, which is right
for an `allow` and wrong for everything else: appending one byte to calldata
un-matched a `deny` rule while leaving a broader `allow` matching, and the
target contract's decoder ignores the byte and performs the call. Matching is
now three-valued — see `Match` — and an `allow` requires certainty while a
`deny` needs only suspicion.

**`183234`** was closed by removing a feature rather than versioning it. The
maintainer's call: `is_token` and `is_address_book` are gone from the predicate
language. Those two stores exist to tell a person what they are looking at, and
reading them into an authorization decision gave one row two jobs — a token
confirmed so a transfer would read `1.0 USDC` also widened what signed without
asking, and nothing afterwards could tell the two uses apart. `PolicyContext`
is now a single address.

## Known work

Three findings are real and deliberately left, with the analysis on each in
V12 rather than only here.

`183268` is the one to do first. `validate_signed_execution` accepts a plain
EIP-1559 envelope for a Calibur batch without asserting the wallet actually
holds a delegation — and a batch targets the wallet itself, so against an
undelegated EOA it succeeds trivially and does nothing. The receipt says
success and the documented atomic-batch guarantee is silently not delivered.
The fix needs the simulation (or chain state) at a function that currently
takes neither, and it guards what gets broadcast.

`183277` and `183267` share a root: failure results synthesize fields they
never observed. `will_authorize_delegation` is inferred from execution mode
rather than from the wallet's code, and gas is absent entirely, so an override
of a setup error fails with "simulation did not provide gas usage". Both want
the same change — a `SimulationResult` that distinguishes "observed and absent"
from "never determined" — threaded through the fifteen call sites reaching
`base_failure_result`.

`183259`'s second half is also open: the database key is published to the
credential store before the database file exists, so a crash between them
leaves an orphan. It self-heals (the next open regenerates) and risks no
wallet key, since private keys are separate entries.

## Two decisions worth restating

**Gas is unpoliced.** `native_value` guards what a call *sends*, not what it
costs, and no predicate scores gas. The only bound that does not depend on the
endpoint's honesty is the network profile's `max_gas_limit`, which every
built-in preset sets and a custom network must. That is the whole of the answer
to `183248` and `183249`, and `docs/networks.md` now says so.

**Metadata is display, and only display.** After `7810980` the token database
and address book decide nothing. The `tests/boundary.rs` tripwire on their MCP
write paths stays anyway: an agent that could name an address would still
choose the sentence the owner reads while deciding, which is the same outcome
by a different route.
