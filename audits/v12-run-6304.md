# V12 run 6304 — resolution log

Full audit of `main@7177cef`. 4 critical, 76 high, 270 medium, 146 low = 496.
Run: <https://v12.sh/runs/6304>.

Counts are the ones the run reported while still consolidating; it emitted 752
findings and then spent hours merging duplicates downward (752 → 552 → 517 →
510 → 496) without adding any. Nothing below depends on the tail of that
process: the criticals were stable across every snapshot, and the highs lost
only duplicates.

Every finding is verified against current `main` before it is fixed. The audit
predates six commits, three of them security fixes, so some findings in
`rpc.rs`, `cli.rs`, and `approval_summary.rs` may already be closed — those are
marked as such only after checking, and the unexamined ones are listed as such
rather than assumed either way.

## The theme

One sentence covers the four criticals and most of the highs fixed so far:

> **A value is trusted because of where it arrived, not because anything
> established that it is what it claims to be.**

The name a thing arrives under is stable enough to look like an identity and
reusable enough not to be one; an answer arrives in response to a question and
is taken as an answer *to that question*; a state is inferred from an error
rather than asked about. Each fix below is the same move — bind the value to
the thing it is supposed to be about, at a place every user of it must pass.

**Identity by name.**
A wallet id is reusable, so `delete(wallet_id)` deletes whatever occupies the
id when it lands rather than the key its caller meant (203741, 203743, 203740).
A pathname is rebindable, so `set_permissions(path)` narrows whatever the name
resolves to now rather than the file that was opened, and `path.exists()`
answers a different question than the open that follows (203688). An envelope
and its hash arrived as two strings and were only checked against each other on
the way back out (203563, 203556). A broadcast hash named a transaction the row
did not hold (203568), and an envelope's presence did not have to match the
lifecycle state that implies it (203567).

**An answer assumed to be about the question.**
A receipt lookup names a hash and took whatever came back as the receipt for it
(203529) — the purest case, and the one with the widest blast radius, since
every terminal settlement runs through that function and no terminal state is
ever reconciled again. A quorum stopped listening once it had heard enough
(203348), and its medians sampled only the first responders (203349) and
counted witnesses from other chains (203350). A delegation observed at
simulation time was still believed at send time (203335), and an endpoint that
read a header and then failed still chose the block everyone else simulated
against (201318).

**An error read as knowledge.**
A credential store that fails does not say whether it failed before or after
doing the thing, and every place that guessed guessed the same way — that
nothing happened. That guess destroyed keys in one direction (203740) and
orphaned them in the other (203742). A rejection that could not be written was
reported the same way whether it had landed or not (203439). A token that
declined its balance probe vanished from the review rather than being named
(203341), and a failed simulation asserted delegation facts it had never
observed (203339).

The repository already knew about the third of these; the comments in `add` and
`remove` argue it at length, and run 6207's critical (`183231`) is the same bug
in the same function. **It recurred because the fixes reasoned at the call site
rather than establishing an invariant the callee enforced.** That is the single
most useful conclusion here, and it is what shaped every fix in this pass.

### The fix hierarchy this produced

Preferred in this order, because each level binds strictly more future code
than the one below it:

1. **Make the bad state unwriteable.** `KeyStore::delete(id)` is gone;
   `delete_matching(id, expected)` is the only deletion. `VerifiedEnvelope` has
   one constructor, so bytes and hash cannot be held apart long enough to
   disagree. `set_private_file_permissions` was deleted rather than corrected.
2. **Put the check on the boundary every reader crosses**, not in one writer.
   `PendingRow::parse` over `mark_broadcast`'s guard; `transaction_receipt`
   over each of its callers. A writer's guard protects one path; a boundary
   protects the paths written next year.
3. **Extract the decision into a pure function** when the branch that matters
   is one no fixture can easily reach: `rpc::quorum_verdict`,
   `custody::classify_failed_write`, `execution::authorization_for_send`,
   `simulation::unverified_token_probes`.
4. **Use exhaustive matches** so a new variant forces a decision
   (`envelope_requirement`, `PendingStatus::is_terminal`), and where a SQL
   literal list mirrors an enum, hold the two together with a test
   (`terminal_statuses_match_the_enum`).

Adding a check at the call site is the last resort — and it is what most of
these findings, read literally, were asking for.

### What the test suite revealed

Worth recording separately, because it cuts both ways and the next person will
meet it.

**Where the tests were permissive, they were permissive in exactly the
direction of the defect.** `fee_history_stub` documented that
`median_fee_estimate` never checks `eth_chainId` — true when written, and
precisely the gap. Every `m_of_n` median test set `agree` equal to the number
of live endpoints, so the truncated sample and the full one were the same
sample and no sampling was exercised at all. A cancellation test passed a junk
hash for the envelope whose *stale pricing* it was asserting. In each case a
test going red during a fix was the test admitting what it had been allowing.

**But not always.** When the lifecycle invariant (203567) was first written to
say every state from `signed` onward carries an envelope, two existing tests
refused it — correctly. `cancelled` has two honest origins, and the rule needed
three arms. A red test means "look", not "the test is wrong".

The practical consequence: **every fix in this pass was verified by reverting
it and confirming the new test fails.** Two regression tests passed against the
bug on first writing and had to be rewritten — one because the endpoint
ordering made the truncated and full samples agree, one because the expected
fee was miscalculated. A regression test that passes against the defect is
worse than no test, and neither would have been caught by review.

### 203741, 203743, 203740 — the wallet lifecycle

All three reproduce at HEAD by reading `custody.rs`; `custody.rs` and
`config.rs` are untouched by the six post-audit commits.

`OsKeyStore::insert_new` split `get_secret` from `set_secret`, so two creations
of one id could both pass the absence check and both write. The loser of the
subsequent configuration race called `delete(wallet_id)` with no proof the
entry was still its own, and destroyed the winner's key. `remove` bound the
reviewed address to its metadata deletion but let that guard expire before
`keys.delete(wallet_id)`, so a wallet created in the gap inherited the id and
lost its brand-new key to an approval given for its predecessor. And any error
from deletion sent the rollback down a path that restored the row
unconditionally — listing a wallet whose only key was already gone.

Fixed two ways, either of which closes all three:

- **`KeyStore::delete(id)` is gone.** `delete_matching(id, expected)` is the
  only deletion, and a store that finds a different address returns
  `Mismatched` and leaves it alone. `address_of` answers what is stored without
  conflating "no credential" with "could not read". A caller can no longer
  write "delete whatever is under this name".
- **`ConfigStore::with_lifecycle_lock`** makes the credential write and the
  configuration write one cross-process step. A separate lock file, because
  `update` runs inside it and `flock` deadlocks against a second descriptor for
  the same file. `remove` takes it *after* owner authentication: holding a
  cross-process lock for as long as a human takes to answer a prompt is its own
  defect, and the identity binding is what makes the pre-lock window safe.

A failed deletion now probes the store and restores the row only on positive
proof the reviewed key survived. Key gone means the removal happened and the
row stays gone; unreadable says so instead of guessing.

Regression tests (`custody_test.rs`):
`deletion_is_addressed_by_key_rather_than_by_name`,
`a_deletion_that_destroyed_the_key_before_failing_does_not_relist_the_wallet`,
`a_deletion_that_kept_the_key_restores_the_row`,
`an_unreadable_credential_store_does_not_relist_the_wallet`,
`a_creation_that_loses_the_configuration_race_keeps_the_winners_key`.

### 203688 — path resolution

Three separate name resolutions, each answerable differently:
`create_private_dir` used `exists`/`metadata` (both follow links) and applied
0700 to whatever a planted symlink pointed at; `PolicyStore::production`
decided whether a database existed with a second `path.exists()` separate from
the open that followed, so a swap between them turned "this database exists and
its key is gone" into "no database, mint a key" and left the original
unopenable; and `set_private_file_permissions` chmodded the database by name
*after* the connection was open.

- `create_private_dir` asks `symlink_metadata` and **refuses** a symlinked data
  directory rather than hardening it. The wallet cannot promise 0700 on a
  directory whose identity another process picks.
- `set_private_file_permissions` is **deleted**, not corrected. Its one caller
  now uses `open_private_file`: `O_NOFOLLOW`, and the mode applied to the
  handle. There is no longer a way to chmod a private file by path.
- Existence comes from the handle, and from its length rather than its
  presence — a zero-length file is a database with nothing in it yet, so a
  stray empty file from a failed first run does not brick the next one.

Regression tests (`config_test.rs`):
`a_symlinked_data_directory_is_refused_rather_than_hardened`,
`a_private_file_is_opened_through_the_name_it_was_given`.

**Behaviour change worth knowing:** a data directory reached through a symlink
is now refused with an explanatory error. This is intended, but anyone whose
`--data-dir` is a link will see it.

## High — resolved so far

| uid | title | verdict | commit |
|---|---|---|---|
| 203742 | Ambiguous credential writes orphan private keys | fixed | `3aa7426` |
| 203744 | Removal approval is not bound to the reviewed wallet address | fixed | `df7f571` |
| 201701 | Stale Review Crosses Wallet Name Reuse (`custody.rs`) | fixed | `df7f571` |
| 203348 | Quorum accepts results before checking all contradictory witnesses | fixed | `9d7a479` |

**203348** is *not* closed by `71a0a5b`, despite that commit landing in the same
area — it added tests for `median_fee_estimate` and `median_head`, not for
`agree_across_endpoints`. Both quorum loops returned as soon as one answer
collected `required` witnesses, which made their own contradiction branches
unreachable exactly when a contradiction existed. `agree_across_endpoints`
documents that "a genuine disagreement fails closed"; with `m_of_n(2)` over
three endpoints, the two agreeing endpoints ended the loop and the third was
never asked, so whether a disagreement was noticed depended on visit order —
under `random`, a coin flip per request. The simulation quorum had the
identical shape and decides what an automatic signature is evaluated against.

Neither loop returns early now, and the decision itself moved into one function
(`rpc::quorum_verdict`) that both read. The two had already drifted into making
the same mistake independently; a shared rule is what stops it recurring.

The regression test was confirmed to fail against the previous behaviour — it
returned 500 rather than refusing — and pass after. The pre-existing
contradiction test could not have caught this: with `agree` equal to the
endpoint count, the quorum is only ever reached on the last endpoint, so the
early return never fired.

**Cost note for the maintainer:** `m_of_n` now costs one request per configured
endpoint rather than `agree` requests. That is the price of the documented
fail-closed guarantee, but it is a real change to a latency-sensitive path.

### 203337, 203339 — EIP-7702 delegation disclosure

| uid | title | verdict | commit |
|---|---|---|---|
| 203337 | Untrusted RPC response can hide delegation replacement | fixed | `e8cf80d` |
| 203339 | Failed simulations can conceal EIP-7702 delegation replacement | fixed | `e1fbf78` |

One shared cause: **the only disclosure a delegation ever had was
`delegation_replaced`, and whether it fired depended on an observation that
may be dishonest or may never have happened.**

`get_code_at(wallet)` decides both `needs_override` and `replaces`. An endpoint
that reports empty code for an account that is really delegated elsewhere takes
the `None if wallet_code.is_empty()` branch: the authorization is still signed,
the replacement still happens on chain, and `replaces` stays `None`, so nothing
in the document mentions delegations at all (203337). Separately,
`base_failure_result` set `will_authorize_delegation` from the execution mode
alone with `replaces_delegated_implementation: None` — and a failure can happen
before the wallet code is ever read, so that `None` means "nobody looked", not
"nothing to replace" (203339). A failed simulation is exactly the case a human
overrides, and the review draws its replacement warning from that same field.

Both now emit `delegation_authorized`, a new **warning**, whenever an
authorization would be signed — with a message that says which of the two
situations produced it. Warning rather than error is deliberate: every
account's first batch authorizes a delegation, so `RequiresApproval` there
would mean no unattended batch could ever run. It never displaces
`delegation_replaced` when both apply.

Worth noting how these interact with `9d7a479`: under `m_of_n` the delegation
facts are part of the `SimulationAgreement` projection, so no single endpoint
can move them — but only now that the quorum actually hears every endpoint
before deciding. Before that fix, two endpoints agreeing early ended the vote
and the honest third was never asked.

Tests: `authorizing_a_first_delegation_is_disclosed_without_blocking_the_batch`
(`policy_test.rs`), `a_failed_batch_says_the_delegation_was_never_observed`
(`simulation_test.rs`).

**Not fixed:** corroborating `get_code_at` under `ordered`, where one endpoint
is authoritative for everything by documented design — see `RpcStrategy`'s own
doc comment. The disclosure above is what remains under that strategy.

### 203349 — the sample a quorum median is taken over

| uid | title | verdict | commit |
|---|---|---|---|
| 203349 | Partial head sampling lets one RPC pin stale simulation state | fixed | `67e572a` |

The third and fourth instances of 203348's mistake, in two more functions.

`median_head`'s doc comment states the property it exists for: "A median with a
majority honest is a height an honest endpoint reported, and one liar moves it
by at most a position." True of a median over the whole set. It stopped at
`required`, so the sample was the first responders — and a liar is fast. With
`m_of_n(2)` over three endpoints, one stale endpoint answering alongside one
current endpoint is half the sample, `median` takes the lower of the two middle
values, and the stale height wins. The honest third endpoint is never asked.
Every endpoint then simulates against the height the liar chose and agrees
honestly about it: the quorum is real and the state agreed on is the
attacker's.

`median_fee_estimate` had the identical `break`, on the number that reaches the
chain rather than the screen. An endpoint answering below the market carries a
truncated even sample the same way, and an automatic transaction priced under
it sits in the mempool holding the wallet's one in-flight slot.

Both now sample every configured endpoint, keeping the `>= required` floor. All
four `m_of_n` paths now cost one request per configured endpoint and mean the
same thing by a quorum.

Both regression tests were confirmed to fail against the previous behaviour.
The existing median tests could not have caught this: each configures `agree`
equal to the number of live endpoints, so the truncated sample and the full one
are the same sample. That is worth remembering when reading the other `m_of_n`
tests — a quorum test whose threshold equals its endpoint count exercises no
sampling at all.

### 202009 — a failed observation read as an empty chain

| uid | title | verdict | commit |
|---|---|---|---|
| 202009 | Timeout Releases Potentially Accepted Transaction | fixed | `169692c` |

`reconcile_failed_send` reduced both post-rejection lookups with
`.ok().flatten()`, so a timeout and a transport error arrived as the same
`false` that an honest "the node does not hold it" produces.
`send_failure_outcome` then set `broadcast_error`, and `submit_claimed`
released the submission lease on it — putting the row back to `signed`, where
it is retryable and discardable.

A raw-send timeout can happen **after** the node accepted the transaction. So
the sequence turns "we could not tell" into "it is not there", frees the
in-flight slot, and invites the owner to discard or replace an envelope that
may still mine at its nonce.

`Presence` now has three answers and `absence_established` carries the third to
the one place that acts on it. The failure is still reported either way — the
caller asked for a send and did not get one — but an unobserved absence no
longer buys a lifecycle transition.

Unobserved **keeps the lease**, rather than choosing `broadcast`. That is
deliberate: recording a broadcast that never happened freezes the account on
that chain, which is the failure the existing comment argues against at length
and is right about for the case it names. Staying `submitting` defers to the
stale-lease machinery, which exists for exactly this — it lapses and the next
pass settles on an observation instead of a guess.

The three existing tests moved from `bool` to `Presence` and now say which of
the two meanings of `false` each of them meant. A fourth was added for the
answer that had nowhere to go.

### 203569 — a lease with time still to run

| uid | title | verdict | commit |
|---|---|---|---|
| 203569 | Unbounded wall-clock timestamps control submission leases | fixed | `d3b15af` |

`submission_lease_expired` compares `Utc::now() - record.updated_at` against
the 120-second interval, and `updated_at` is a durable wall-clock value with no
plausibility bound in the schema or in row decoding. A row stamped in the
future — a clock that jumped and came back, a database copied between machines,
a restored backup — gives a *negative* age, which against that comparison reads
as a lease with time still to run. `submitting` holds the wallet's one
in-flight slot, so the wallet is frozen on that chain until wall time catches
up to the stamp and *then* the lease elapses.

What decided the direction of the fix is that the two failure modes are not
symmetric. Recovering too early is **bounded**: every recovery transition is a
compare-and-set on `generation`, so a recovery racing a live submitter loses
rather than corrupting it. Refusing to recover is **unbounded** and needs a
human with a SQL prompt. So a negative age is treated as expired rather than as
infinitely fresh.

`lease_expired` takes the age rather than reading the clock — the case worth
testing is the age nobody expected.

### 203529 — a receipt for some other transaction

| uid | title | verdict | commit |
|---|---|---|---|
| 203529 | Unverified receipt identity can forge transaction settlement | fixed | `391d5c7` |

`transaction_receipt` names a hash in the request and validated the endpoint's
chain ID and the receipt's own fields — but never that the returned receipt
identifies that hash. `try_endpoints` takes the first successful response, so
one same-chain endpoint could make an unrelated receipt authoritative.

Every terminal settlement runs through this one function. `observe` treats any
receipt as `Mined`; `reconcile_cancelling` finalizes the original or marks the
request cancelled from one; the CLI's rebroadcast and discard paths reconcile
first and act on the status that produces. **None of those terminal states is
reconciled again**, and reaching one releases the in-flight slot. So an
endpoint answering with another transaction's receipt settles a still-live
envelope, and the real one mines with nothing watching it.

One check at the adapter, so every caller gets it — inside the `try_endpoints`
closure, matching the reasoning already written there: an endpoint that answers
about the wrong transaction is *that endpoint* failing, and the next is still
asked.

Test: `a_receipt_for_another_transaction_is_not_an_answer`, over a new
`receipt_stub`. It pins the honest case too, so the check is not simply
refusing everything.

### 203570 — history nothing reclaimed

| uid | title | verdict | commit |
|---|---|---|---|
| 203570 | Unbounded terminal transaction history exhausts the wallet database | fixed | `96dba6e` |

`MAX_AWAITING_APPROVALS_PER_WALLET` bounds the queue and the partial unique
index bounds what is in flight, but nothing bounded what those rows *become*.
Every automatic signature writes a durable row before it broadcasts, so
repeated valid requests grow the shared database and its indexes without limit
— and when writes fail they fail for every wallet in the store, taking signing,
reconciliation, policy changes and recovery with them. `list`'s `LIMIT` bounds
what a caller is shown, not what is kept.

`prune_terminal_history` drops a wallet's oldest finished rows past 1000, on
the two insert paths, inside the caller's transaction — history is reclaimed by
the same activity that produces it rather than by a sweep somebody has to
remember to run. Only terminal rows, and only past the cap: anything awaiting a
decision, signed, in flight, or cancelling is live state, and deleting one
would lose an envelope the chain may yet mine.

The pruning runs in SQL against `TERMINAL_STATUSES`, so that list is what
decides. `PendingStatus::is_terminal` answers the same question exhaustively
for a parsed value, and `terminal_statuses_match_the_enum` holds the two to
each other — adding a state to one and forgetting the other would either leak
history forever or delete a row the lifecycle still needs.

### 203567 — an envelope the state implies

| uid | title | verdict | commit |
|---|---|---|---|
| 203567 | Enforce lifecycle-bound signed transaction invariants | fixed | `5ea3cc4` |

`PendingRow::parse` checked that the envelope and its hash were both present or
both absent and that they agreed, but never that either matched the status the
row claims.

The expensive half is an in-flight row with no envelope. `signed`,
`submitting`, `broadcast`, and `cancelling` all hold the wallet's one in-flight
slot, and nothing can move such a row on: `claim_for_submission` leases any
`signed` row without looking, `submit_claimed` then fails constructing
`SignedExecution` before reaching its lease-release handling, and reconciliation
cannot take a nonce from a record with no bytes. `reconcile_all` keeps the
record on error, so the slot is held until someone repairs the database.

The quiet half is the converse: `rejected` is reachable only from
`awaiting_approval`, so signed bytes on one are bytes that should not exist and
are readable through the ordinary transaction reads.

`envelope_requirement` is an exhaustive match, so a new lifecycle state is a
decision someone makes in the one place that says what an envelope means.

**It has three arms because the tests said so.** A first attempt asserted that
every state from `signed` onward carries an envelope, and two existing tests
refused it: `cancelled` has two honest origins — `discard_unsent` from a
`signed` row never submitted, which has its bytes, and wallet-state removal
cancelling `awaiting_approval` rows, which never had any. Worth recording as
the counterpoint to the permissive-fixture pattern below: here the suite was
right and the new rule was wrong, which is exactly what a good suite is for.

The broadcast-hash half of this finding was fixed separately in `d89bcd1`.

### 203568 — a hash the row did not own

| uid | title | verdict | commit |
|---|---|---|---|
| 203568 | Bind broadcast hashes to their signed envelopes | fixed | `d89bcd1` |

`PendingRow::parse` required `serialized_transaction` to hash to
`signed_transaction_hash` and said nothing about `broadcast_transaction_hash`.
The schema constrains both hashes by shape only, and `mark_broadcast`'s
equality guard — its `UPDATE` matches on `signed_transaction_hash = ?2` — is a
property of that one writer, not of the row.

That field is read by code which trusts it completely: `reconcile` looks a
receipt up by `broadcast_transaction_hash` in preference to the signed hash,
while `observe` derives the nonce from `serialized_transaction`. A row where
those disagree settles this plan from **another transaction's** receipt — or
its absence — as mined, reverted, or replaced. The in-flight slot is released
while the envelope actually signed is still pending and may yet mine, and
`recheck_replaced` repeats the same preference so it can miss the real
envelope's receipt too.

The invariant now sits beside its sibling in `PendingRow::parse`, the boundary
every reader crosses — the same reasoning that put the serialized/signed check
there rather than in the writers. A guard in one writer protects one path; an
invariant on the row protects every reader, including the ones written later.

Test: `a_broadcast_hash_naming_another_transaction_is_refused_on_read`, which
plants the mismatch with a direct `UPDATE` because no writer will produce one.
That is the point — the threat is an altered or externally written row, not a
bug in `mark_broadcast`. Confirmed to fail with the invariant removed.

### 203439 — a refusal that was only on the screen

| uid | title | verdict | commit |
|---|---|---|---|
| 203439 | Failed rejection persistence leaves requests signable | fixed | `6889725` |

By the time the rejection is written, the presenter has already drawn "refused"
on the reviewer's terminal. The row decides whether that is true:
`store_signed` accepts anything still `AwaitingApproval`, so a rejection that
did not commit leaves a request the owner declined available to a later
approval flow, which can sign it. The error went to the caller; the owner had
already been told the opposite.

The ordering was already right — the rejection is the first thing after the
decision, deliberately, and the comment there says why. What was missing is
that two different outcomes were reported identically. `reject` commits and
*then* re-reads, so a failure in that read means the rejection **did** land
while the caller hears an error.

`record_rejection` asks the row which happened. Already `Rejected` is a success
that reported itself badly, and is returned as one. Anything else is a
rejection that genuinely is not recorded, and the error now says so in the
owner's terms: still awaiting approval, still signable, and the command to
refuse it again.

Tests: `a_rejection_already_recorded_is_a_success_not_an_error` (a second
rejection stands in for the post-commit read failure) and
`a_rejection_that_did_not_land_says_the_request_can_still_be_signed`. New
`rejection_tests` module per the second-module naming rule in `CLAUDE.md`.

### 203563 — a pair that could disagree

| uid | title | verdict | commit |

| 203563 | Commit-time envelope/hash validation is missing | fixed | `0e8167e` |

`record_automatic_signed`, `store_signed`, and `store_cancellation` each took
the serialized envelope and its claimed hash as separate strings, parsed each
on its own, and wrote both. `keccak256(bytes) == hash` was enforced only by
`PendingRow::parse` — on the way back *out*.

A well-formed but mismatched pair therefore committed, and only the `self.get`
after the commit failed. The row is durable and unreadable, and `signed` and
`cancelling` both hold the wallet's one in-flight slot through the partial
unique index. `reconcile_all` swallows the read error to keep a listing
rendering, so the slot stays held and nothing further can be signed for that
wallet on that chain until the database is repaired by hand. When the wedged
row is a *cancellation*, the owner is locked out while trying to stop a
transaction.

`validate_signed_execution` already contains this exact check; the persistence
boundary never called it. Rather than add the call three times, the pair is now
one value — `VerifiedEnvelope`, one constructor, which refuses a disagreement.
No writer holds the bytes and the hash separately long enough for them to
drift, and reintroducing the two-argument shape means deleting a type rather
than forgetting a line.

Test: `a_mismatched_envelope_and_hash_never_reach_the_database`, which also
asserts the slot is still free afterwards and the cancellation writer still
progresses — the wedge is the actual harm, not the rejected write.

**203556 is the same finding, decomposed.** "Validate cancellation envelope
hashes before committing state" states the cancellation writer's half of what
203563 states across all three, so `0e8167e` closes both and the test already
exercises `store_cancellation` specifically. Recorded as fixed rather than
duplicate: it is a real defect and it is really closed, and calling it a
duplicate would hide that the cancellation writer is the worst of the three to
wedge.

| uid | title | verdict | commit |
|---|---|---|---|
| 203556 | Validate cancellation envelope hashes before committing state | fixed | `0e8167e` |

**Third fixture found encoding the defect.**
`cancellation_reprices_on_one_row_until_an_attempt_mines` passed a junk hash
for the envelope whose *stale pricing* it was asserting, because a mismatched
pair did not matter before. It now passes that envelope's own hash, so the
assertion tests what it names. Together with `fee_history_stub` (203350) and
the median tests (203349), that is a pattern worth stating: **where this
codebase's tests were permissive, they were permissive in exactly the direction
of the defect.** A test going red during one of these fixes is usually the test
admitting what it had been allowing.

### 201318 — a pin left behind by an endpoint that failed

| uid | title | verdict | commit |
|---|---|---|---|
| 201318 | Failed Simulation Attempt Freezes Retry Pin | fixed | `310da4d` |

The first chain-valid endpoint's observed parent was promoted to the shared
`pin` before its result was classified. If that endpoint then failed during the
pinned-state reads or `eth_simulateV1`, the loop failed over — discarding its
answer but keeping its height, and forcing the healthy retry to simulate there.
An endpoint could report an old header, fail the request on purpose, and choose
the state a later honest endpoint evaluates against without ever producing a
simulation at all.

The promotion could only ever fire under a single-answer strategy; `m_of_n`
sets `pin` from `median_head` before the loop, and a fork pins its own parent.
Its justification — under one answer the height is that endpoint's anyway —
holds only while that endpoint's answer is the one used, which is precisely
what a failover means it is not.

**This one has no new test, deliberately.** `pin` is now an immutable binding,
so the promotion cannot be reintroduced without changing the binding itself,
and `a_single_answer_strategy_pins_nothing` already asserts `median_head`
returns `None` under `ordered` and `random`. Together those prove `pin` is
`None` for the whole single-answer path — the compiler covers the half a test
would have. A runtime test needs a stub `eth_simulateV1` endpoint, which this
repository does not have: every simulation test is an `#[ignore]`d
live-network one.

**Recommended next infrastructure:** that stub harness. `rpc_test.rs` already
has the pattern (`stub_endpoint`, `fee_history_stub`), and the remaining
`simulation.rs` and `pending.rs` findings will each want it. Building it once
is cheaper than the assertions their absence forces.

### 203341 — a token that answers nothing

| uid | title | verdict | commit |
|---|---|---|---|
| 203341 | Fail closed when token balance probes are incomplete | fixed | `aace468` |

`token_balance_results` turns a reverted or undecodable `balanceOf` into
`None`. With no standard `Transfer` log to fall back on,
`token_balance_changes` drops the token from the change set entirely, and the
orchestrator renders an empty change set from an otherwise *successful*
simulation as "none detected". A token that declines its probe and emits no
recognized event therefore moves a balance and appears nowhere in the review.

The display is the smaller half. The tokens probed here are the ones the
**policy** sets limits on, and a limit cannot be enforced against a number the
wallet does not have — so the automatic path had neither the number nor any
sign that it was missing. That is what makes failing closed proportionate here
rather than noisy: the set is scoped to tokens an owner wrote a limit for.

Reported as an error, naming each token. Only tokens absent on *both* sides
count: one side present already places the token in the change set where a
reader will see it, which is not the silent case.

Tests: `a_token_that_answers_neither_probe_is_named_rather_than_dropped` over
the extracted `unverified_token_probes`, plus
`an_unreadable_token_balance_stops_the_automatic_path` for the outcome. The
helper is extracted because reaching this branch needs an adversarial token and
no fixture has one.

### 203350 — a witness on another chain

| uid | title | verdict | commit |
|---|---|---|---|
| 203350 | Unverified RPC heads can poison the simulation pin | fixed | `ce20dcc` |

The other half of the same two functions. Both called `provider_for(endpoint)`
directly and took whatever came back; nothing requires every configured
endpoint to serve the configured chain, since `validate_network` checks the
shape of the RPC list rather than its identity. An endpoint on another chain
reported that chain's height, and that height entered the median that pins the
whole quorum.

What makes this one worth reading twice: `simulate_execution_through` *does*
check the chain, and its comment explains carefully that `observed_parent` is
written only after the check, so an endpoint about to be disqualified cannot
choose where the quorum simulates. That reasoning is correct and arrives too
late — by then the pin came from `median_head`, which never checked at all.
Disqualifying an endpoint from simulating does not unmake the pin it already
chose. **A vote cannot be taken back out of a median.**

`ensure_serving_chain` already existed for exactly this and simply was not
reached from here. Both medians now ask for the chain in the same round trip
as the answer and skip a witness that is not on it — a missing witness, like a
dead endpoint, counting toward neither the median nor the quorum.

`fee_history_stub` had to change: it deliberately answered only
`eth_feeHistory`, on the stated grounds that `median_fee_estimate` never checks
`eth_chainId`. A test fixture encoding an assumption the fix invalidates is
worth noticing — the comment was accurate when written and is what made the gap
easy to miss.

Test: `median_head_refuses_a_witness_serving_another_chain`, confirmed to fail
against the previous behaviour, plus the fee-path twin.

### 203335 — the delegation at send

| uid | title | verdict | commit |
|---|---|---|---|
| 203335 | Revalidate delegation before sending recorded simulations | fixed | `0c3f726` |

The third member of the delegation family, and the one that needed a fix in
`execution.rs` rather than a disclosure. A recorded simulation can be sent
minutes after it was produced, and nothing in between rereads the account's
code: `validate_send` checks the wallet, the chain, the policy revision, the
plan digest, and the fork flag, and none of those move when a delegation does.
`prepare_execution` therefore took `authorize_delegation` from
`simulation.will_authorize_delegation` — the account as it was at simulation
time.

If the account acquired a delegation since, the Calibur payload is interpreted
by code nobody simulated or reviewed. If it lost one, the transaction spends a
nonce and fees on a batch that cannot execute. And on the failed-simulation
path the flag was asserted from execution mode alone with nothing observed —
which is the result a human is asked to override.

The read now happens in `prepare_execution`, the one choke point every send
passes through, so the recorded path, the queued-approval path, and the
automatic path are covered together. A changed *reviewed* context refuses the
send rather than being silently recomputed. An account already delegated to
canonical Calibur now skips the authorization instead of paying a nonce for a
no-op, which the stale flag could not express.

Test: `a_delegation_that_moved_after_simulation_refuses_the_send`, over
`authorization_for_send` — extracted for the same reason `quorum_verdict` was,
since the branch that mattered only exists between a simulation and a send at
different times.

**203742** is the mirror of 203740: `set_secret` returning an error was read as
"nothing was written", and `add` returned before writing metadata or running
any rollback, stranding a committed key with no row naming it — invisible to
`account list` and enough to fail the next creation as a duplicate.
`classify_failed_write` turns a readback into the four outcomes that exist
(committed, not written, conflicting, cannot tell) and is a free function so
all four are testable without a platform credential store, which is why only
one of them was ever considered. Test:
`a_write_that_reported_an_error_is_classified_by_what_the_store_holds`.

**203744 and 201701** are fixed at the level that matters: after `df7f571` a
removal cannot *act* on anything other than the reviewed address. Both writes
are guarded — the configuration update refuses a row whose address changed, and
`delete_matching` refuses a credential that is not the reviewed one — so an
approval can no longer be spent on a replacement. It fails instead.

What is deliberately **not** changed is the platform dialog text. Both findings
observe that the owner is shown a wallet *name*, and adding the address would
make the binding visible to the human rather than only enforced in code. That
is a real improvement, but `PresenceRequest::reason` documents the opposite
rule on purpose — "It says which wallet and what will happen to it — nothing
else. A digest here told the reader nothing they could check and buried the one
clause they could." Overriding a documented UX decision is the maintainer's
call, not an audit sweep's. **Recommendation:** show a short address form
(`0x1234…cdef`) in `RemoveWallet` and `ExportPrivateKey` only — the two
irreversible key operations — as the stated exception to that rule.

## A note on the gate

`cargo test --workspace` cannot complete unattended on macOS:
`tests/credential_store_startup.rs` runs the real CLI, which blocks on a
Keychain prompt and hangs indefinitely (observed at 0% CPU for 18 minutes on
clean `main`, before any change here). Everything above was gated with

```sh
cargo fmt
cargo clippy --workspace --all-targets      # clean
cargo test --workspace --lib --bins \
  --test boundary --test example_policies \
  --test local_reference --test shipped_assets   # 829 passed, 0 failed
```

CI runs the excluded test on Linux, where the credential store does not prompt.
Worth marking it `#[ignore]` locally or gating it on an environment variable so
the documented gate actually terminates on a developer machine.
