# V12 run 6304 — resolution log

Full audit of `main@7177cef`. 4 critical, 76 high, 270 medium, 146 low = 496.
Run: <https://v12.sh/runs/6304>.

Counts are the ones the run reported while still consolidating; it emitted 752
findings and then spent hours merging duplicates downward (752 → 552 → 517 →
510 → 496) without adding any. Nothing below depends on the tail of that
process: the criticals were stable across every snapshot, and the highs lost

Every finding is verified against current `main` before it is fixed. The audit
predates six commits, three of them security fixes, so some findings in
`rpc.rs`, `cli.rs`, and `approval_summary.rs` may already be closed — those are
marked as such only after checking, and the unexamined ones are listed as such

## The theme

One sentence covers the four criticals and most of the highs fixed so far:

> **A value is trusted because of where it arrived, not because anything
> established that it is what it claims to be.**

The name a thing arrives under is stable enough to look like an identity and
reusable enough not to be one; an answer arrives in response to a question and
is taken as an answer *to that question*; a state is inferred from an error
rather than asked about. Each fix below is the same move — bind the value to
the thing it is supposed to be about, at a place every user of it must pass.

**Identity by name.**
A wallet id is reusable, so `delete(wallet_id)` deletes whatever occupies the
id when it lands rather than the key its caller meant (203741, 203743, 203740).
A pathname is rebindable, so `set_permissions(path)` narrows whatever the name
resolves to now rather than the file that was opened, and `path.exists()`
answers a different question than the open that follows (203688). An envelope
and its hash arrived as two strings and were only checked against each other on
the way back out (203563, 203556). A broadcast hash named a transaction the row
did not hold (203568), and an envelope's presence did not have to match the
lifecycle state that implies it (203567).

**An answer assumed to be about the question.**
A receipt lookup names a hash and took whatever came back as the receipt for it
(203529) — the purest case, and the one with the widest blast radius, since
every terminal settlement runs through that function and no terminal state is
ever reconciled again. A quorum stopped listening once it had heard enough
(203348), and its medians sampled only the first responders (203349) and
counted witnesses from other chains (203350). A delegation observed at
simulation time was still believed at send time (203335), and an endpoint that
read a header and then failed still chose the block everyone else simulated
against (201318).

**An error read as knowledge.**
A credential store that fails does not say whether it failed before or after
doing the thing, and every place that guessed guessed the same way — that
nothing happened. That guess destroyed keys in one direction (203740) and
orphaned them in the other (203742). A rejection that could not be written was
reported the same way whether it had landed or not (203439). A token that
declined its balance probe vanished from the review rather than being named
(203341), and a failed simulation asserted delegation facts it had never
observed (203339).

**A check trusted for where it was put.**
The mirror image of the other three, and the reason they recur. The policy
language's admission checks were real and correct, but they lived on
`WalletPolicy::parse` rather than on the type, so the derived `Deserialize`
built the same authority-bearing object having passed none of them (201724).
Nothing was wrong with the checking; what was wrong was that a reader had to
arrive by the right door to meet it. The same shape is why a guard on
`mark_broadcast` did not protect rows written by anything else (203568), and
why `create_private_dir` hardening one path left `open_private_file`'s callers
uncovered (203688), and why `build.rs` refusing a symlink during its walk did
not bind the lookup rustc performed afterwards (203661). Its clearest instance is 202446, where
`install.sh` verifies the archive, the checksums, and the signature over the
checksums, and nothing verified `install.sh` — the care taken inside the script
is what made the gap around it invisible. Its plainest is 203365: the wallet-has-a-policy
invariant was enforced by a loop over the wallets that existed when the server
started, so a wallet created afterwards was one the check had never seen.

The repository already knew about the third of these; the comments in `add` and
`remove` argue it at length, and run 6207's critical (`183231`) is the same bug
in the same function. **It recurred because the fixes reasoned at the call site
rather than establishing an invariant the callee enforced.** That is the single
most useful conclusion here, and it is what shaped every fix in this pass.

### The fix hierarchy this produced

Preferred in this order, because each level binds strictly more future code
than the one below it:

1. **Make the bad state unwriteable.** `KeyStore::delete(id)` is gone;
   `delete_matching(id, expected)` is the only deletion. `VerifiedEnvelope` has
   one constructor, so bytes and hash cannot be held apart long enough to
   disagree. `set_private_file_permissions` was deleted rather than corrected.
   `WalletPolicy`, `ChainPolicy`, and `Rule` validate inside `Deserialize` and
   are `#[non_exhaustive]`, so outside the kernel there is no way to build one
   that passed nothing.
2. **Put the check on the boundary every reader crosses**, not in one writer.
   `PendingRow::parse` over `mark_broadcast`'s guard; `transaction_receipt`
   over each of its callers. A writer's guard protects one path; a boundary
   protects the paths written next year.
3. **Extract the decision into a pure function** when the branch that matters
   is one no fixture can easily reach: `rpc::quorum_verdict`,
   `custody::classify_failed_write`, `execution::authorization_for_send`,
   `simulation::unverified_token_probes`.
4. **Use exhaustive matches** so a new variant forces a decision
   (`envelope_requirement`, `PendingStatus::is_terminal`), and where a SQL
   literal list mirrors an enum, hold the two together with a test
   (`terminal_statuses_match_the_enum`).

Adding a check at the call site is the last resort — and it is what most of
these findings, read literally, were asking for.

### What the test suite revealed

Worth recording separately, because it cuts both ways and the next person will
meet it.

**Where the tests were permissive, they were permissive in exactly the
direction of the defect.** `fee_history_stub` documented that
`median_fee_estimate` never checks `eth_chainId` — true when written, and
precisely the gap. Every `m_of_n` median test set `agree` equal to the number
of live endpoints, so the truncated sample and the full one were the same
sample and no sampling was exercised at all. A cancellation test passed a junk
hash for the envelope whose *stale pricing* it was asserting. In each case a
test going red during a fix was the test admitting what it had been allowing.

**But not always.** When the lifecycle invariant (203567) was first written to
say every state from `signed` onward carries an envelope, two existing tests
refused it — correctly. `cancelled` has two honest origins, and the rule needed
three arms. A red test means "look", not "the test is wrong".

The practical consequence: **every fix in this pass was verified by reverting
it and confirming the new test fails.** Two regression tests passed against the
bug on first writing and had to be rewritten — one because the endpoint
ordering made the truncated and full samples agree, one because the expected
fee was miscalculated. A regression test that passes against the defect is
worse than no test, and neither would have been caught by review.

### 203741, 203743, 203740 — the wallet lifecycle

All three reproduce at HEAD by reading `custody.rs`; `custody.rs` and
`config.rs` are untouched by the six post-audit commits.

`OsKeyStore::insert_new` split `get_secret` from `set_secret`, so two creations
of one id could both pass the absence check and both write. The loser of the
subsequent configuration race called `delete(wallet_id)` with no proof the
entry was still its own, and destroyed the winner's key. `remove` bound the
reviewed address to its metadata deletion but let that guard expire before
`keys.delete(wallet_id)`, so a wallet created in the gap inherited the id and
lost its brand-new key to an approval given for its predecessor. And any error
from deletion sent the rollback down a path that restored the row
unconditionally — listing a wallet whose only key was already gone.

Fixed two ways, either of which closes all three:

- **`KeyStore::delete(id)` is gone.** `delete_matching(id, expected)` is the
  only deletion, and a store that finds a different address returns
  `Mismatched` and leaves it alone. `address_of` answers what is stored without
  conflating "no credential" with "could not read". A caller can no longer
  write "delete whatever is under this name".
- **`ConfigStore::with_lifecycle_lock`** makes the credential write and the
  configuration write one cross-process step. A separate lock file, because
  `update` runs inside it and `flock` deadlocks against a second descriptor for
  the same file. `remove` takes it *after* owner authentication: holding a
  cross-process lock for as long as a human takes to answer a prompt is its own
  defect, and the identity binding is what makes the pre-lock window safe.

A failed deletion now probes the store and restores the row only on positive
proof the reviewed key survived. Key gone means the removal happened and the
row stays gone; unreadable says so instead of guessing.

Regression tests (`custody_test.rs`):
`deletion_is_addressed_by_key_rather_than_by_name`,
`a_deletion_that_destroyed_the_key_before_failing_does_not_relist_the_wallet`,
`a_deletion_that_kept_the_key_restores_the_row`,
`an_unreadable_credential_store_does_not_relist_the_wallet`,
`a_creation_that_loses_the_configuration_race_keeps_the_winners_key`.

### 203688 — path resolution

Three separate name resolutions, each answerable differently:
`create_private_dir` used `exists`/`metadata` (both follow links) and applied
0700 to whatever a planted symlink pointed at; `PolicyStore::production`
decided whether a database existed with a second `path.exists()` separate from
the open that followed, so a swap between them turned "this database exists and
its key is gone" into "no database, mint a key" and left the original
unopenable; and `set_private_file_permissions` chmodded the database by name
*after* the connection was open.

- `create_private_dir` asks `symlink_metadata` and **refuses** a symlinked data
  directory rather than hardening it. The wallet cannot promise 0700 on a
  directory whose identity another process picks.
- `set_private_file_permissions` is **deleted**, not corrected. Its one caller
  now uses `open_private_file`: `O_NOFOLLOW`, and the mode applied to the
  handle. There is no longer a way to chmod a private file by path.
- Existence comes from the handle, and from its length rather than its
  presence — a zero-length file is a database with nothing in it yet, so a
  stray empty file from a failed first run does not brick the next one.

Regression tests (`config_test.rs`):
`a_symlinked_data_directory_is_refused_rather_than_hardened`,
`a_private_file_is_opened_through_the_name_it_was_given`.

**Behaviour change worth knowing:** a data directory reached through a symlink
is now refused with an explanatory error. This is intended, but anyone whose
`--data-dir` is a link will see it.

## High — resolved so far

| uid | title | verdict | commit |
|---|---|---|---|
| 203742 | Ambiguous credential writes orphan private keys | fixed | `3aa7426` |
| 203744 | Removal approval is not bound to the reviewed wallet address | fixed | `df7f571` |
| 201701 | Stale Review Crosses Wallet Name Reuse (`custody.rs`) | fixed | `df7f571` |
| 203348 | Quorum accepts results before checking all contradictory witnesses | fixed | `9d7a479` |

**203348** is *not* closed by `71a0a5b`, despite that commit landing in the same
area — it added tests for `median_fee_estimate` and `median_head`, not for
`agree_across_endpoints`. Both quorum loops returned as soon as one answer
collected `required` witnesses, which made their own contradiction branches
unreachable exactly when a contradiction existed. `agree_across_endpoints`
documents that "a genuine disagreement fails closed"; with `m_of_n(2)` over
three endpoints, the two agreeing endpoints ended the loop and the third was
never asked, so whether a disagreement was noticed depended on visit order —
under `random`, a coin flip per request. The simulation quorum had the
identical shape and decides what an automatic signature is evaluated against.

Neither loop returns early now, and the decision itself moved into one function
(`rpc::quorum_verdict`) that both read. The two had already drifted into making
the same mistake independently; a shared rule is what stops it recurring.

The regression test was confirmed to fail against the previous behaviour — it
returned 500 rather than refusing — and pass after. The pre-existing
contradiction test could not have caught this: with `agree` equal to the
endpoint count, the quorum is only ever reached on the last endpoint, so the
early return never fired.

**Cost note for the maintainer:** `m_of_n` now costs one request per configured
endpoint rather than `agree` requests. That is the price of the documented
fail-closed guarantee, but it is a real change to a latency-sensitive path.

### 203337, 203339 — EIP-7702 delegation disclosure

| uid | title | verdict | commit |
|---|---|---|---|
| 203337 | Untrusted RPC response can hide delegation replacement | fixed | `e8cf80d` |
| 203339 | Failed simulations can conceal EIP-7702 delegation replacement | fixed | `e1fbf78` |

One shared cause: **the only disclosure a delegation ever had was
`delegation_replaced`, and whether it fired depended on an observation that
may be dishonest or may never have happened.**

`get_code_at(wallet)` decides both `needs_override` and `replaces`. An endpoint
that reports empty code for an account that is really delegated elsewhere takes
the `None if wallet_code.is_empty()` branch: the authorization is still signed,
the replacement still happens on chain, and `replaces` stays `None`, so nothing
in the document mentions delegations at all (203337). Separately,
`base_failure_result` set `will_authorize_delegation` from the execution mode
alone with `replaces_delegated_implementation: None` — and a failure can happen
before the wallet code is ever read, so that `None` means "nobody looked", not
"nothing to replace" (203339). A failed simulation is exactly the case a human
overrides, and the review draws its replacement warning from that same field.

Both now emit `delegation_authorized`, a new **warning**, whenever an
authorization would be signed — with a message that says which of the two
situations produced it. Warning rather than error is deliberate: every
account's first batch authorizes a delegation, so `RequiresApproval` there
would mean no unattended batch could ever run. It never displaces
`delegation_replaced` when both apply.

Worth noting how these interact with `9d7a479`: under `m_of_n` the delegation
facts are part of the `SimulationAgreement` projection, so no single endpoint
can move them — but only now that the quorum actually hears every endpoint
before deciding. Before that fix, two endpoints agreeing early ended the vote
and the honest third was never asked.

Tests: `authorizing_a_first_delegation_is_disclosed_without_blocking_the_batch`
(`policy_test.rs`), `a_failed_batch_says_the_delegation_was_never_observed`
(`simulation_test.rs`).

**Not fixed:** corroborating `get_code_at` under `ordered`, where one endpoint
is authoritative for everything by documented design — see `RpcStrategy`'s own
doc comment. The disclosure above is what remains under that strategy.

### 203349 — the sample a quorum median is taken over

| uid | title | verdict | commit |
|---|---|---|---|
| 203349 | Partial head sampling lets one RPC pin stale simulation state | fixed | `67e572a` |

The third and fourth instances of 203348's mistake, in two more functions.

`median_head`'s doc comment states the property it exists for: "A median with a
majority honest is a height an honest endpoint reported, and one liar moves it
by at most a position." True of a median over the whole set. It stopped at
`required`, so the sample was the first responders — and a liar is fast. With
`m_of_n(2)` over three endpoints, one stale endpoint answering alongside one
current endpoint is half the sample, `median` takes the lower of the two middle
values, and the stale height wins. The honest third endpoint is never asked.
Every endpoint then simulates against the height the liar chose and agrees
honestly about it: the quorum is real and the state agreed on is the
attacker's.

`median_fee_estimate` had the identical `break`, on the number that reaches the
chain rather than the screen. An endpoint answering below the market carries a
truncated even sample the same way, and an automatic transaction priced under
it sits in the mempool holding the wallet's one in-flight slot.

Both now sample every configured endpoint, keeping the `>= required` floor. All
four `m_of_n` paths now cost one request per configured endpoint and mean the
same thing by a quorum.

Both regression tests were confirmed to fail against the previous behaviour.
The existing median tests could not have caught this: each configures `agree`
equal to the number of live endpoints, so the truncated sample and the full one
are the same sample. That is worth remembering when reading the other `m_of_n`
tests — a quorum test whose threshold equals its endpoint count exercises no
sampling at all.

### 203615 — the peer chose what was forgotten

| uid | title | verdict | commit |
|---|---|---|---|
| 203615 | Peer-controlled IDs allow replay-cache eviction and request reexecution | fixed | `930b4f6` |

The WalletConnect replay set evicted by numeric id, justified in its own
comment: *"Protocol ids are microsecond-scale timestamps, so the lowest is the
oldest"*. They usually are — but the id is a `u64` the **peer** chooses, and
this set is the only thing between a captured envelope and a second execution
of the request inside it.

So the peer picked what was forgotten. A settled dapp sends enough high-valued
answerable messages to push out the low id it used earlier, replays the
authenticated envelope carrying that id, and `remember` reports it as new.
`on_request` dispatches it again, and a policy-allowed `eth_sendTransaction`
reaches simulation, signing and broadcast a second time at a fresh nonce with
no new review — the transfer happens twice.

`AnsweredIds` keeps arrival order beside membership: a queue says which entry
came first, a set answers whether an id is present. **Arrival order is not
something a peer can address.** The bound, the redelivery reasoning and the
memory argument are unchanged; only the choice of what to drop is.

**Third false guarantee in a comment**, after `InteractiveProof` (203267) and
`open_in_browser` (203409) — and the most consequential of the three, because
it reads as settled reasoning about a protocol rather than an implementation
detail. The existing test asserted the numeric rule and repeated the same
justification, the fifth fixture found encoding the defect beside it.

### 203409 — a shell where the comment promised there was none

| uid | title | verdict | commit |
|---|---|---|---|
| 203409 | Windows explorer URLs are executed through `cmd.exe` | fixed | `65b88ac` |

`open_in_browser` documented that "the URL is passed as a single argument to a
fixed program, never through a shell". On Windows it was `cmd /C start ""`, and
`cmd.exe` reparses its command line for `&`, `|`, `^` **after** Rust has
finished quoting arguments. The URL was command syntax, not data.

That base comes from a network profile an MCP caller can propose, and
`validate_network` checked only the scheme. An accepted profile could run
commands as the wallet's user the first time the owner pressed `o` on a
transaction — and the review screen never showed the explorer URL, so there was
nothing to notice at the moment of consent.

Fixed at the sink, the door, and the screen: `rundll32
url.dll,FileProtocolHandler` gives Windows the same fixed-program one-argument
shape the other platforms already had; `validate_network` refuses a query
string or fragment on either informational URL (a base is a base —
`explorer_transaction_url` appends `/tx/{hash}`, so anything after `?` would be
discarded anyway, and refusing it removes the ordinary place an `&` can
legitimately appear); and the review shows the explorer base, being the one
field there that becomes an argument to another program.

**This is the second false guarantee stated in a comment**, after 203267's
`InteractiveProof`. Both were load-bearing — a reader who believed either would
stop looking exactly where the defect was. Worth its own line in the theme: a
comment asserting a security property is a claim that needs checking like any
other, and in this codebase two of them were wrong.

The Windows launcher cannot be exercised from macOS; it is a three-line change
to a fixed program name and CI builds it. The validation is tested.

### 203794 — the same clock mistake, in a second place

| uid | title | verdict | commit |
|---|---|---|---|
| 203794 | Rollbackable clock can extend simulation validity | fixed | `cddbc81` |

A recorded simulation's 120-second lifetime is wall-clock arithmetic:
`expires_at = now + TTL`, compared later against another wall-clock reading.
Wall clocks move backwards, and against a later reading alone a rollback makes
an entry look *younger* than it is and keeps it sendable past its window. The
production path hands in `Utc::now()`, so nothing supplies monotonicity.

A `now` before `recorded_at` says the clock moved — the one thing this can
detect without a monotonic source — and such an entry is now pruned.

**This is 203569 again in a different file**, and the comment says so. Both are
a duration computed from a subtractable clock where the negative case was read
as the most favourable one rather than the least trustworthy: there a lease
with time still to run, here a simulation still fresh. Worth noting as a
sub-pattern of *an error read as knowledge* — an impossible measurement is
information, and both sites discarded it.

The clock stays injected rather than read inside the store, which is what makes
the rollback testable at all. A monotonic `Instant` deadline would close the
residual window where the clock moves back but stays after `recorded_at`, at
the cost of that testability — noted rather than taken.

### 203424 — a recipient nothing checked

| uid | title | verdict | commit |
|---|---|---|---|
| 203424 | Zero-address recipients permit irreversible transfers | fixed | `7c72cd3` |

`Transfer.to` was unrestricted and `transfer_plan` used it directly — as the
transaction target for a native transfer, and as the recipient encoded into
ERC-20 `transfer` calldata.

Sending the native token to `0x0` destroys it. For a token the outcome depends
on which contract was named, since many ERC-20s burn the amount rather than
refusing the call — so whether the value survives is a property of the
counterparty rather than of the request. That is not a thing to leave to chance
in a plan the wallet signs.

Refused before the plan is built rather than left to the policy, because **no
policy rule speaks about it**: an ordinary allowlist for the token authorizes
this plan, and `ExecutionPlan::validate` checks calldata bounds, step ordering,
chain, and sender — everything about the shape of the request except where the
value is going. One bad recipient refuses the whole batch, since the plan is
signed as a unit.

### 203447 — a wrapper that edited what it displayed

| uid | title | verdict | commit |
|---|---|---|---|
| 203447 | Review wrapping omits signed whitespace at line boundaries | fixed | `1a7fbbf` |

`wrap_line_hanging` emitted the text before the space it broke at and resumed
at `space + 1`, so that character appeared on no visual row. Ordinary prose
wrapping — and wrong here, because this wrapper renders the complete EIP-712
payload a person reads before signing, and a space inside a JSON string literal
is part of the value the digest commits to.

A requester placing a meaningful space at a reachable wrap boundary had it
vanish with no continuation marker, so the string on the screen was not the
string being signed.

The break space now stays on the row it ended. That costs an unnoticeable
trailing space and buys the property that matters: **the rendered document
contains every character of its input.** Laying text out is this function's
job; editing it is not. Fixing the shared wrapper covers every caller.

`wrapping_prefers_a_space_and_keeps_blank_lines` asserted the old behaviour —
the fourth fixture in this sweep found encoding the defect beside it. The new
tests sweep every width from the minimum to past the input length, so the
boundary lands in every position, over inputs with leading, trailing and
doubled spaces.

### 203446 — an authorization that is not an allowance

| uid | title | verdict | commit |
|---|---|---|---|
| 203446 | Render SignatureTransfer authorizations distinctly from allowances | fixed | `83a3ff9` |

Permit2 `PermitTransferFrom` and `PermitBatchTransferFrom` were rendered
through the same sentence as standing allowances — "allow X to spend up to Y of
token Z" — although the decoder has always known the difference and records it
in `kind`.

A SignatureTransfer creates nothing the owner can later inspect or revoke: the
spender consumes it once, to a recipient chosen when they execute it. Calling
that an allowance tells the reader to expect a thing that will not exist, and
to go looking for a revocation that is not there.

Both sentences now live in `permit_grant_sentence`, testable without building a
request, a wallet and a configuration to reach them, and a warning appears when
any one-time authorization is present.

The fourth withdrawal, and the second overridden under the rule stated at
203445: the check here is one line — `kind` distinguishes the two and the
renderer ignored it.

### 203445 — two clocks, one label

| uid | title | verdict | commit |
|---|---|---|---|
| 203445 | Permit2 approval review omits allowance expiration | fixed | `38ccbd9` |

Permit2 carries two clocks and the review reported one of them under a name
that fits the other. `sigDeadline` bounds only how long the *signature* may be
submitted; `PermitDetails.expiration` is how long the *allowance* it grants
stays usable, per token. The decoder read the first and dropped the second —
`expiration` appeared nowhere in `typed_data.rs` outside the two type-string
constants — and the review rendered `sigDeadline` as "deadline".

So a permit could show a deadline minutes away while granting a standing
authority lasting until the maximum `uint48`. The reviewer reads "deadline
soon", approves, the spender submits before that deadline and then draws on the
allowance for as long as its real expiration allows. A batch can also give one
token an allowance that lapses within the hour and another that effectively
never does, under one signature.

The two clocks are now named differently — "signature usable until X" and
"ALLOWANCE LASTS UNTIL Y" — and the shapes with only one clock (ERC-2612, DAI,
and Permit2 signature transfers, which grant no standing allowance) report
nothing rather than inventing a limit.

**Disagreement with the run's own triage, recorded rather than resolved
silently.** This finding was reclassified to `low`/`invalid` while this pass was
running — the third the run withdrew unprompted. Unlike 203573 and 203565, it
was fixed anyway: the defect reproduces on main and is visible in three facts —
the field is read nowhere, the struct has nowhere to put it, and the renderer
labels the wrong clock "deadline". Where a withdrawal can be checked against
the code and the code disagrees, the code wins; where it cannot be cheaply
checked, the withdrawal stands. Both of those are judgement calls the
maintainer may want to revisit.

### 203448 — the narrower copy of a check that already existed

| uid | title | verdict | commit |
|---|---|---|---|
| 203448 | Incomplete Unicode filtering permits deceptive review text | fixed | `4d36b05` |

Two halves, and the first is the now-familiar shape.

`escape_for_display` — the message-signing review — tested
`is_control() || is_bidirectional_control()`, a narrower copy of *part* of the
shared predicate. So every invisible-format character passed through
unescaped: a zero-width space splitting `1 0` into what reads as `10`, a
variation selector changing a glyph, a tag block encoding a whole ASCII string.
**This is the display where being unable to see a character is the entire
attack, and it was the one display not using the full check.** It calls
`is_disallowed` now, and the warning list gained a line for invisible and
glyph-changing characters beside the existing bidi one.

Second, `is_invisible_format` was missing the characters the finding names —
U+034F, U+2065, U+206A–U+206F, U+FFF9–U+FFFB, and the variation selectors at
U+FE00–U+FE0F and U+E0100–U+E01EF. The variation selectors matter as much as
the zero-width ones and are less obvious: they choose which glyph the preceding
character wears, so two byte-distinct values can render identically with no
character of their own to see.

**The standing weakness is that this is a denylist**, and everything in it was
added because somebody noticed. `std` exposes no Unicode general category, so
the honest options are the list or a `unicode-*` dependency carrying the Cf and
Mn tables. That is now written into the doc comment rather than left implicit:
the characters that matter are exactly those two categories, and if the list
grows again the dependency is the better answer, because enumerating by hand
will keep losing to the next revision of the standard.

### 203506, 203507, 203511, 203518 — the wallet-identity family, known work

| uid | title | verdict |
|---|---|---|
| 203511 | Wallet lifecycle permits stale policy authority on ID reuse | **known work** |
| 203506 | Stale wallet cleanup deletes replacement state | **known work** |
| 203507 | Incomplete wallet retirement can transfer stale policy state | **known work** |
| 203518 | Policy approvals can apply to a replacement wallet | **known work** |

Four findings, one root cause, and it is the same sentence as the criticals:
**policy-store state is keyed on a reusable `wallet_id` and bound to nothing
that identifies the wallet.** `wallet_policies`, `policy_proposals`, and the
three request queues all key on the name; `PolicyStore::get` returns authority
for a name; MCP startup checks only that a name *has* a policy. A replacement
wallet with a different address and a different key answers to all of it.

Custody publication and policy initialisation are also separate commits, in
different layers: `custody.create/import` returns, and then `src/cli.rs` calls
`initialize_wallet_policy`. A plan submitted in that window, or after a removal
whose `purge` failed, can be simulated and automatically signed under the
predecessor's policy — with the replacement's key.

**`df7f571` does not close this**, and it is worth being explicit about why,
because the two look adjacent. `ConfigStore::with_lifecycle_lock` serializes
custody operations against each other, so the credential and the inventory row
move together. It does not extend to the policy steps, which happen in the CLI
after custody returns — and it cannot simply be wrapped around them, because
`custody.create` takes that same lock internally and `flock` on a second
descriptor for one file deadlocks against the descriptor this process already
holds. Composing them needs the policy work to run *inside* the lock custody
already holds, not around it.

That is the narrowest useful step, and it is a real API change rather than a
patch: `CustodyService` would need a form of `create`/`import`/`remove` that
takes what to do with the new or retired identity and runs it before releasing
the lock. It closes the **race** half — creation, import and removal become one
cross-process transition — without touching the schema.

The **authority** half needs more: an address or generation column on the
policy and queue rows, written on creation and verified on every read, plus a
recovery path that fails closed when the binding is absent or does not match.
That is a schema bump this build cannot migrate, on the same footing as 203401,
and it changes what `PolicyStore::get` means to every caller.

Recorded as known work rather than attempted. A partial identity binding in a
wallet's authority model is the worst of the three states: it looks like the
property holds, and the paths that do not carry the binding are exactly the
ones nobody thought about.

### 203440 — every failure read as "not in this queue"

|---|---|---|---|

### 203401 — known work, not a sweep fix

| uid | title | verdict |
|---|---|---|
| 203401 | Reorgable chain observations permanently settle transaction lifecycles | **known work** |

Real, and not fixed here. `finalize`, `mark_cancelled`, and `mark_replaced`
commit a single latest-RPC observation as a durable terminal state, and
`reconcile_record` then returns terminal rows unchanged — so a reorg, or a
transient receipt-index/nonce inconsistency, leaves a record permanently
reporting an outcome that is no longer canonical, with the in-flight slot
already released.

What the finding asks for is a reorg-aware, finality-qualified lifecycle. That
is four separate decisions, each the maintainer's:

2. **A provisional/final distinction in the status model.** `confirmed` today

   what every reader of the status means by it, including the MCP surface.
3. **Rollback transitions.** `recheck_replaced` already exists to walk back a

   currently moves a row *out* of `confirmed`, and the in-flight unique index
   would have to re-acquire a slot that was released.
4. **A finality depth per network.** There is no such setting, and the right
   value differs per chain.

Half-implemented finality in a wallet's settlement path is worse than none: a
rollback that fires when it should not is a wallet freeing a slot for a
transaction that did execute. Recorded as known work rather than attempted.

**The narrowest useful first step**, if the maintainer wants one: store the
receipt's block hash next to `block_number`. It is inert on its own, costs one
column, and is the prerequisite every other part of the above needs. Everything
else can follow once the finality policy is decided.

### 203569 — a lease with time still to run

| uid | title | verdict | commit |
|---|---|---|---|
| 203569 | Unbounded wall-clock timestamps control submission leases | fixed | `d3b15af` |

`submission_lease_expired` compares `Utc::now() - record.updated_at` against
the 120-second interval, and `updated_at` is a durable wall-clock value with no
plausibility bound in the schema or in row decoding. A row stamped in the
future — a clock that jumped and came back, a database copied between machines,
a restored backup — gives a *negative* age, which against that comparison reads

human with a SQL prompt. So a negative age is treated as expired rather than as
infinitely fresh.

`lease_expired` takes the age rather than reading the clock — the case worth
testing is the age nobody expected.

An endpoint could report an old header, fail the request on purpose, and choose
the state a later honest endpoint evaluates against without ever producing a
simulation at all.

The promotion could only ever fire under a single-answer strategy; `m_of_n`
sets `pin` from `median_head` before the loop, and a fork pins its own parent.
Its justification — under one answer the height is that endpoint's anyway —
holds only while that endpoint's answer is the one used, which is precisely
what a failover means it is not.

**This one has no new test, deliberately.** `pin` is now an immutable binding,
so the promotion cannot be reintroduced without changing the binding itself,
and `a_single_answer_strategy_pins_nothing` already asserts `median_head`
returns `None` under `ordered` and `random`. Together those prove `pin` is
`None` for the whole single-answer path — the compiler covers the half a test
would have. A runtime test needs a stub `eth_simulateV1` endpoint, which this
repository does not have: every simulation test is an `#[ignore]`d
live-network one.

**Recommended next infrastructure:** that stub harness. `rpc_test.rs` already
has the pattern (`stub_endpoint`, `fee_history_stub`), and the remaining
`simulation.rs` and `pending.rs` findings will each want it. Building it once
is cheaper than the assertions their absence forces.

### 203335 — the delegation at send

| uid | title | verdict | commit |
|---|---|---|---|

The third member of the delegation family, and the one that needed a fix in

### 201724 — a second door into the same type

**high, fixed in `856a333`.** The policy language's semantic checks — version,
chain keys, the 4096-call batch ceiling, label lengths, and whether each
predicate is applicable to the slot holding it — hung off `WalletPolicy::parse`.
The type also derived `Deserialize`. So `serde_json::from_value::<WalletPolicy>`
built the same authority-bearing object having passed none of them, and
`evaluate_policy` read `max_calls_per_batch` from whatever it was handed without
asking: a directly deserialized `5000` authorizes automatic signing of a batch
four thousand calls past the documented ceiling. The same door admitted
predicates never checked against their slots — a `length` predicate on `to`
decides nothing, so a rule the owner reviewed as a restriction restricts
nothing.

Not reachable today: every caller goes through `parse`, and the finding says so
itself. What was broken is that the invariant was unenforceable at the type
boundary, which is a defect with a shelf life — the next caller to accept
untrusted JSON is the one that pays for it.

The fix is the first rule of the hierarchy below, applied twice. Each of
`WalletPolicy`, `ChainPolicy`, and `Rule` now deserializes through a private
mirror of its own fields and then validates itself, so `parse` and `from_value`
are the same door rather than one checked and one not. And each invariant moved
to the type that owns it rather than living in the outermost container: the
ceiling, the label, and `native_value` applicability on `ChainPolicy`; the slots
on `Rule`; version, schema URL, and chain keys on `WalletPolicy`. A `ChainPolicy`
lifted out of a fragment on its own is now checked by the code that checks one
reached through a document.

`#[non_exhaustive]` closes the other half, which the finding's own root cause
names and which is the easier bypass: writing the struct literal. Nothing
outside the core crate constructed one and field reads are unaffected, so what
it forecloses is exactly the construction of a policy that passed nothing.
Together, an invalid `WalletPolicy` cannot be held outside the security kernel
at all.

**Maintainer-visible:** `#[non_exhaustive]` on three public types of
`ekubo-wallet-core` is a semver-breaking API change. The workspace is the only
consumer and `1.0.0-rc.0` is the moment to make it, but it is a consequence of
an audit sweep rather than a design decision, and it is reversible if the crate
is ever meant to be built against from outside.

The mirrors are the one thing this fix adds that can rot, so they carry
`deny_unknown_fields`: a field added to a public type and forgotten in its
mirror is rejected on the first document that uses it rather than quietly
skipping validation, and a round-trip test over a document naming every field
is what notices. Four of the five new tests fail against the previous
behaviour, verified by reverting.

One incidental find: the paragraph explaining the invariant, written first as a
doc comment on `Rule`, was copied by `schemars` straight into
`schemas/policy.schema.json` — the document policy authors read. The shipped-asset
test caught it. It is a `//` comment now.

### 203365 — a guarantee that held for one of the three signing paths

**high, fixed in `3ab28f6`.** `account create` and `account import` write the
wallet into `config.json` and only then initialize its policy. A failure
between the two leaves a wallet whose key exists and whose authority was never
described, and the CLI says what that state means: *"it has no policy, so
signing fails closed and the MCP server refuses to start until it has one."*
`cli.rs` states it again as a fact, in a comment justifying how a policy diff is
rendered — *"that is what `no policy` means to every signing path: nothing is
permitted."*

It was true for transactions, because grading a plan needs a policy to grade it
against. It was not true for the two payloads no policy can score. Off-chain
signing consults no policy by design — a policy cannot say what a permit
authorizes, so a person reads every one — but *consults no policy* had quietly
become *does not need one to exist*. The only enforcement of the invariant was
a loop in `WalletMcpServer::new` over the wallets present at startup, while
every request resolves its wallet from `config.json` as it stands now. A wallet
half-provisioned under a running server was invisible to that loop, and the
server would queue and sign its EIP-712 payloads — a permit, an order, a
delegation, exercised by the recipient at their leisure — for an owner who had
been told the wallet was inert.

The fourth shape again, and the clearest instance of it: the check was real,
it was simply in a place that only some readers cross.

`orchestrator::require_provisioned_wallet` now runs first in both
`sign_reviewed_message` and `sign_reviewed_typed_data`, ahead of owner
authentication — a wallet that will be refused must not put a prompt on the
owner's screen, because that prompt is the wallet asserting it is prepared to
do the thing. Both signers take the policy store and re-read it at signing
time rather than trusting a caller's earlier look, which is the rule the rest
of that ladder already follows ("a re-read of every mutable input the review
may have raced"). The MCP tools refuse up front too, so an agent is told no
when it asks rather than after a person has read the payload.

Follow-up in `7ac48f2`: the store was first opened inline at the moment of
signing, which meant a keyring read and a fresh SQLCipher connection per
approval, done after the review had already been drawn. It is now opened
alongside the other request stores and threaded down, so a database that will
not open says so before a person reads a payload. Passing it as a parameter
also made the compiler name a third caller the finding did not list — the
WalletConnect session in `src/connect.rs`, which reaches the same two signers
and is now covered by the same guard.

Note what the guard does *not* do: it asks whether the wallet was ever
finished, not what its policy permits. Off-chain signing still consults no
policy, and should not.

The two behavioural tests fail with the guard removed, verified by removing it.
The positive control passes either way, which is the point of having it — it is
what a signer that refused everything would fail. **Not covered:** the
up-front MCP refusal has no test of its own; the kernel guard behind it does,
and that is the one that decides. **Complement worth doing:** make provisioning
atomic, so the half-provisioned state stops being reachable in the first place.
The guard is the durable half regardless — a restored or hand-edited database
can desynchronize a config file whatever `create` does.

### 203661 — a path checked by one reader and resolved by another

**high, fixed in `68cf555`.** `build.rs` walked `clearsign/` refusing symlinks,
then wrote `include_str!` expressions naming the same paths under
`CARGO_MANIFEST_DIR`. Two readers resolved each path — the build script, which
checked, and rustc some time later, which did not — and only the second one
decided what shipped. Anything able to write to the checkout in between could
replace a checked file, or a directory above it, with a symlink and put bytes
from outside the reviewed tree into the artifact under a path that still reads
as vendored.

The existing check was not wrong, and its comment says exactly what it is for:
*"a single symlink would put bytes from outside this tree into the artifact
under a path that still looks vendored."* It was simply guarding a lookup that
was not the one that mattered. The fourth shape once more, and the third
instance of it this pass.

Worth being clear about the threat model, because it is narrower than the
finding's wording suggests: an attacker who can write to the working tree can
also just edit the descriptors. What the symlink refusal buys is protection
against a *committed* symlink — an innocuous-looking tree entry that passes
review while reaching outside — and the race extends that to a hostile
concurrent process on a shared build host. Both are supply-chain shapes where
the reviewed artifact and the built artifact diverge, which is the one property
this file exists to hold.

The build script now reads the bytes itself and stages them under `OUT_DIR`;
the generated `include_str!` names the staged copy. What was checked and what
ships are the same bytes rather than the same pathname. The read refuses a
symlink at every component on the way down and compares the file before and
after, so one swapped mid-read is refused rather than embedded.

Inlining the 1.7 MB corpus as string literals would have closed it too and was
rejected: roughly four megabytes of generated source for the same guarantee a
file copy gives.

A race cannot be held still by a fixture, so the regression test pins the
property — no generated `include_str!` may name a path in the mutable checkout
— and fails against the previous build script, verified by reverting. A second
test asserts the embedded table is exactly the vendored tree, path for path and
byte for byte, because the staging copy this adds is itself a thing that can be
wrong.

### 202446 — verifying the payload with a script the attacker also chose

**high, fixed in `01d13cb`.** `check_for_updates` handed an agent
`curl -fsSL https://raw.githubusercontent.com/{repo}/{tag}/install.sh | sh`.
The script it fetches is careful: it verifies the archive against `SHA256SUMS`,
`SHA256SUMS` against a keyless Sigstore bundle, and it *refuses* rather than
downgrading when either is missing — its comments argue that at length, and
correctly. None of it applies. A shell begins executing a piped script as it
arrives, so an installer chosen by an attacker runs to completion before any
check written inside it could matter. The release workflow signed the archives
`install.sh` names and did not sign `install.sh`.

This one is the theme in its most concentrated form: every check was real,
every check was in the wrong place, and the thoroughness of the inner checks is
what made the outer gap invisible. A careful reader of `install.sh` comes away
persuaded the install is verified.

The installer now ships as a signed release asset. The publish job checks out
the tag, stages `install.sh` into `dist/`, and the existing sign and verify
loops cover it under the same workflow identity as the archives.
`upgrade_command` downloads it and its bundle from the release assets, checks
the bundle against that identity **at this exact tag**, and runs it only if
`cosign` agrees. No `cosign`, no install — the refusal `install.sh` already
makes about its own downloads, applied one step earlier to itself. `&&`
throughout, so a failed download or verification stops the sequence rather than
falling through to `sh`.

Also changed, because each was a place the old claim was still written down:
the tool instruction now tells the agent not to substitute a shorter one-liner,
`install.sh`'s header stops implying it covers itself, the release notes emit
the verifying form, and `docs/releasing.md` verifies the installer before the
artifacts.

Both changed tests fail against the old command, verified by reverting.
Alongside the exact string the properties are asserted separately — no
`raw.githubusercontent.com`, nothing piped into a shell, `cosign` before the
run rather than after, no `||` fallthrough, the tag inside the identity — so a
future rewording cannot quietly drop one.

**Untested by construction:** the workflow half. Nothing in the repository runs
`release.yml`, so that `dist/install.sh` is staged, signed, and published is
verified by reading. Worth a maintainer's eye before the next release, since a
missing asset makes the new `upgrade_command` fail closed — which is the right
direction, but it fails for everyone.

### 203451 — a character that is not invisible, just not what it looks like

**high, fixed in `07e1c2d`.** Not closed by `4d36b05`, which was checked first:
that commit made the message review use the shared `is_disallowed` predicate
instead of a narrower copy, and `is_disallowed` covers characters that are
invisible or that reorder what follows them. A confusable is neither. Cyrillic
`а` renders as Latin `a`, Greek `ο` as `o`, and a typed-data payload naming
`USDС` with a Cyrillic Es is a different string from one naming `USDC`. The
digest tells them apart; the terminal cannot. The signature that comes back is
then good for the asset, counterparty, venue, or delegation the requester
chose rather than the one the owner read — and unlike the message review, which
shows the raw hex alongside, the typed-data review had no exact representation
at all.

A confusable list was considered and rejected: it is a denylist, it needs
maintaining, and the character it does not know about is the one an attacker
picks. The same argument the `sanitize` doc comment already makes about its own
denylist applies with more force here, because this list would never be
finite.

So the review states the code points instead. Every pretty-printed line that is
not pure ASCII carries its exact form underneath, with a sentence saying why the
extra lines are there. The rendering is kept alongside rather than replaced — an
owner who reads Japanese should still be shown Japanese — and an all-ASCII
payload, which is nearly all of them, reads exactly as it did. That is a
whitelist by construction: the disclosure covers every non-ASCII character
there is or ever will be, so there is no list to keep current.

Two of the four tests fail against the previous renderer, verified by
reverting. The other two are what stop this from becoming noise, and from
replacing the escaping that was already there.

### 203435 — the session settled on an account and stored a name

**high, fixed in `2f4c81d`.** A WalletConnect session settles on a specific
account during the connection review, tells the dapp that address, and measures
every request against it with `refuse_foreign_signer`. It then stores the
request under a wallet id and waits for a person. A wallet id is reusable, so
`account remove` followed by `account create` under the same name during that
wait gives the id a different key. `refuse_replaced_account` catches exactly
this — and only at dispatch, which has already happened. The review reloads the
wallet by id and gets the replacement, so the session's checks measure the old
address while the signature comes from the new key. A payload naming the old
address as its RPC signer passes the session's scope while carrying a permit
whose owner is the account that actually signs it.

This is the *first* theme shape — identity by name — in the one family this
pass had left open, and it is the tractable member of it. The wallet-identity
findings recorded as known work (203506/507/511/518) need a lifecycle lock the
CLI cannot take without deadlocking custody. This one needs no lock, because
the session already holds the answer: it has the settled `WalletMetadata` in
memory and was reloading by id anyway.

Both reviewers now take a `SigningAccount` saying which account the decision is
for, and consult it where they resolve the wallet — before the payload is
interpreted against that address and before anything is drawn. A session passes
`Settled`; the CLI passes `AsRecorded`, which is correct there, since the
request is the whole context and the orchestrator's re-read at signing time
already covers the window after the review. An enum rather than an `Option`, so
a new caller has to decide rather than defaulting into the wrong one.

Worth naming what this does and does not close. The window between review and
signature was already closed. This closes the one between the request and the
review — the long one, because it is as long as a person takes. What it does
not do is make the row itself carry the address; that needs a schema column,
which is the same migration 203401 is waiting on.

The ordering test is the one that matters here: a check consulted after the
payload has been interpreted against the wrong address would still pass the
other two.

### 203452 — partly fixed in `bc9deb9`, the rest is a maintainer call

**high.** Legal acceptance is live state — `LegalStore::status` derives

### 203729 — a disconnect thrown away with the screen that recorded it

**high, fixed in `2f60b2e`.** The quit flag belonged to the `IdleView`.
`suspend_idle` drops that view around every review and `enter_idle` builds a
new one with a fresh `AtomicBool::new(false)`, so a `q`, Escape, or Ctrl-C
landing while relay delivery won the session `select!` set a flag on a view
that was then thrown away, and the replacement started out saying no. The
disconnect was not delayed — it was gone. The dapp stayed connected to a person
who believed they had left, and later requests kept being handled, including
transactions the policy signs automatically, until they managed to quit during
a quieter interval.

Not the theme's usual shape but a close relative: the state had two homes and
the wrong one was authoritative. The fix is the first rule of the hierarchy —
the session owns the flag, every view is handed it, and `IdleView` no longer

Both tests fail against the previous code, verified by reverting. The ownership
is read from the source rather than raced — standing the race up needs a relay,

### 200607 — a signature you can write down without making one

**high, fixed in `657554c`.** `MessageStore::store_signature`,
`TypedDataStore::store_signature`, and `PendingStore::store_signed` were `pub`.
They are the transitions that make a request *answered*, and the row they write
is what every reader and every waiter subsequently reports. Their checks are
about that row — right wallet, right digest, still awaiting, 65 syntactically
valid bytes — and say nothing about whether a person reviewed the payload,
authenticated as the owner, or held the key that produced those bytes.

The kernel already argues this shape at length for key material: `signer`,
`expose_hex`, and `load_matching_signer` are crate-private so presentation code
has no route to a signature. A signature it can *write down* without producing
is the same hole one step later — the queue is the audit and authorization
state, so a forged row is indistinguishable downstream from a real approval.

All three are `pub(crate)` now. The orchestrator was already their only caller,
so nothing else moved: what changed is that nothing else *can* be. Pinned in
`no_signer_or_key_material_escapes_the_kernel` beside the custody
declarations, because widening a `pub(crate)` back to `pub` is a one-word diff
that compiles and breaks nothing — which is the erosion that test exists for.
The pin fails against the previous visibility, verified by reverting.

`store_signed` was not named by the finding; it is the same method for
transactions and was fixed with them, since the class is the point.

### 203508 — the last of the wallet-identity family that could be closed

**high, fixed in `12033cf`.** `export(wallet_id)` resolved a reusable name at
three points — the metadata load, the credential load, and the row the
disclosure is recorded on — and none of them was the identity the owner
approved. There *was* a check: the loaded credential against the loaded
metadata. It is a real check of a different thing. Both are read after the
review, so a remove-and-recreate under the same name before the call produces
two values that agree with each other and with nothing that was on the screen.
An owner reading *"reveal the raw private key for 0xabc…"* could be handed the
key for an address that was never part of it — and this is the one operation in
the tool that cannot be undone. The `exported_at` mark could also land on the
successor while the predecessor's key was returned, misdating for anyone
investigating later which key actually escaped.

Identity by name once more, and the reason it is worth calling out separately
is that it survived a pass that had already fixed this shape twice in the same
file. `delete_matching` exists precisely because `delete(wallet_id)` was this
bug; the reasoning is written out at length in its doc comment three hundred
lines above `export`. The check in `export` looked like the same idea and was
not, which is why reading for the *shape* rather than the presence of a check
is the heuristic that found it.

`export` now takes the reviewed address. It is compared before owner
authentication, so a doomed export does not put a prompt on the owner's screen;
after it, because authentication takes as long as a person takes; against the
credential itself; and against the row the disclosure is recorded on. The
lifecycle lock covers everything after the prompt — the comparisons stay
anyway, because the lock answers concurrency and not time, and is not held
across the prompt.

The race test is the export twin of `a_replacement_wallet_keeps_its_key`, using
the same `PresenceThen` fixture that performs the swap inside the

This closes the reachable half of the wallet-identity family. 203506, 203507,

### 201700 — an ABA the revision number could not see

**high, fixed in `81e9f7c`.** Both policy-application paths — the proposal
review and the direct `policy set` — authorize against a screen naming a wallet
id *and* an address, then apply by id after an owner authentication that takes
as long as a person takes. `PolicyStore::purge` clears the database by name on
`account remove`, so a wallet recreated under that name starts its policy
numbering again at revision 1. A stale review can land on a different wallet's
row with every number matching — matching *because* the sequence restarted,
which is exactly why the revision check cannot see it. The owner authorized a
policy for one key and it would govern another; if it permits automatic
signing, requests for the replacement key cross the approval boundary with
nobody having reviewed that wallet.

Identity by name again, and this one is instructive about how thorough the
existing defences were: `consume_proposal` matches the proposal on five columns
including its millisecond timestamp, `apply_policy` checks the revision, and
`purge`'s doc comment explains at length why reuse of a name must not inherit
anything. All correct, and all about the *row*. None of them is about the
wallet.

`ensure_reviewed_wallet` compares the live row against the metadata the review
was drawn from, consulted after the authentication rather than before, since
the window is the one authentication opens. The whole `WalletMetadata` is
compared rather than the address alone, so `created_at` separates two wallets
that somehow share an address and a field added later is covered by having been
added.

Note the direct `policy set` path was not named by the finding and has the
identical gap; both are fixed, since the class is the point.

### 203389 — a bound that belonged to a dependency's parser

**high, fixed in `35ed495`.** `MAX_POLICY_BYTES` was enforced after the
document had been parsed, validated, and canonically re-serialized, so the work
of rejecting an oversized proposal was proportional to the proposal. And
nothing stated a bound on the shape inside it: `Predicate` recurses through
`each`, `any`, `all`, `not`, and `length`, and every walk over it —
applicability at admission, evaluation at signing, rendering in a review — is a
recursion of that shape.

Worth being accurate about severity, because the finding overstates one part.
The stack was **not** actually unbounded: `serde_json` refuses past 128 levels
while parsing, and every route into these types goes through it. Nor is there
exponential blowup — every walk visits each node once. What is true, and is the
defect worth fixing, is that the bound was a constant inside a dependency's
parser rather than a property of this type. It says nothing about a `Predicate`
reached any other way, it is not something this crate would notice changing,
and it is not what anyone reading `check_applicable` would find.

So the bounds are stated where they are facts about the policy language.
`Predicate::check_size` bounds depth and node count, and the node budget counts
an `in` set's members — one level, enormous sideways, which is the shape depth
alone would miss. Chains per document and rules per chain are bounded beside
them. All of it runs inside `validate`, which since 201724 is every path that
can produce one of these types, so this is the second thing that fix bought.
The byte limit is additionally measured at the MCP boundary before parsing.

Limits are far above anything a person writes — the deepest shipped example
nests four levels — and being far above is the point: this is a backstop, not a
style rule, and a document that trips it is not one anybody was going to
review.

Three of the four tests fail against the previous code, verified by reverting;
the fourth asserts an ordinary four-level policy is still admitted, which is
what a bound set too low would fail.

### 203474, 203480, 203481 — two keystrokes typed at the previous screen

**high, fixed in `e55ece7`.** `confirm_review` is the shared confirmation
behind legal acceptance, policy proposals, network proposals, and direct
network edits. Its decision starts on the safe answer, but a buffered `Tab`
toggles it and a buffered `Enter` returns it, so two keystrokes typed at

The fourth shape once more, and this time the helper was not merely uncalled on
one path — it was called on two of the three. `drain_type_ahead` exists,

call site would have been the wrong fix.

`Screen::enter` is the only route into the alternate screen, so the drain goes

added later, by having taken the terminal rather than by someone remembering.
After `enable_raw_mode`, so the keystrokes are in the queue this drains rather

One fix, three findings: 203480 is the legal-acceptance instance and 203481 the

### 203684 — accepted, and the code's reasoning is right

**high, not fixed, and deliberately.** `save` discards `sync_parent`'s result,
so a configuration can be reported saved before its directory entry is durable.
The window is real: a power loss between the rename and the fsync loses a write
the caller was told had landed.

Propagating the error is what the finding recommends and it is the wrong fix
here. The rename has already committed by that point, and the paragraph
directly above it in `save` says why that matters: *"a caller that hears 'the
update failed' about a write that committed rolls back something that
happened. `custody::add` deleting the only copy of a private key is that
mistake in its worst form."* That is not hypothetical — it is run 6207's
critical, and 203740 and 203742 in this run. Adding a `?` here would trade a
rare lost configuration row for a reachable destroyed key.

Surfacing it without failing would need a diagnostic channel, and the kernel
crate has none by design — `core_crate_has_no_presentation_dependencies` is a
test. Adding a logging dependency to the security kernel for a best-effort
durability warning is not proportionate.

So the residual is accepted knowingly, and the comment at the discard now says
that, in those terms, ending with *"do not 'fix' this by adding a `?`"* —
because the plausible future regression here is someone reading the finding and
obliging.

### 203533 — a chain id is not an identity for a set of nodes

**high, fixed in `40a9796`.** One profile is configured per chain id, and
`replace_configured_network` takes a chain over — its doc comment argues for
that, correctly, on the grounds that a chain id identifies a network more
firmly than a name does. What follows from it is that the endpoints behind a
chain id can be swapped wholesale while every pending row keeps pointing at
that id, and a stale, isolated, or forked endpoint set reports the same number.

`transaction discard` is the one destructive lifecycle command — it drops
tracking for an envelope that may still mine — and its whole basis is what the
configured node says about the hash. Resolved by chain id alone it could ask
endpoints that never saw the transaction, receive the answer a node also gives
for one that does not exist, and untrack a viable envelope while it can still
consume its nonce.

Identity by name, in the one place the name is a number. And, again, the data
needed was already persisted: `PendingTransaction` records `network_name` and
nothing compared it.

`network_for_record` compares it. That is not proof the endpoints are the same
ones — nothing local can prove that — but it catches what the wallet can see
and fails closed, telling the caller the profile changed and pointing at
restoring it or cancelling on chain. Aliases count, so renaming a network
through a name it already carried is not a replacement; without that the check
would refuse ordinary configurations, and the test for it is the one a
too-strict version fails.

Scoped to `discard` deliberately. Reconciliation and status through a replaced
profile are the same shape and not destructive, and settling a lifecycle from a
wrong endpoint is 203401 — known work, needing a schema change this build
cannot make.

### 203574, 203758 — removing a wallet out from under a live transaction

**high, both fixed in `f6429a9`.** One root. Removal ends in `purge`, which
deletes every pending row under the name — including the exact signed envelope,
the transaction hashes, and the cancellation state that are the only means of
observing, rebroadcasting, or cancelling something already authorized and
possibly already sent. Those bytes do not stop being valid because the wallet
was removed: the transaction can still mine and consume its nonce with nothing
left locally that knows it exists. 203758 is the sharper version — a submission
already claimed by another process holds the envelope in memory, broadcasts
after the row is gone, and its lifecycle write then fails against a row that no
longer exists.

Removal now asks first and refuses while anything is in flight, naming the
transactions and what to do about them.

**The check is deliberately not inside `purge`,** which is worth recording
because the fix hierarchy above would normally say to put it there. `purge` has
a second caller, at wallet *creation*, and its comment argues correctly that
erasing is right there: the previous key is already gone, and refusing would
leave the name permanently unusable with no way to clear it. Two callers, two
different correct answers. The one that must refuse is the one about to destroy
a key, so that is where the question is asked.

Ordering matters as much as the check: it runs before the approval prompt and
long before `custody.remove`, because afterwards the key is gone and refusing
helps nobody. That is what the ordering test holds.

`IN_FLIGHT_STATUSES` is the same set the schema's uniqueness index already
treats as live, and a test holds the two together — a status counted as in
flight by the index but not here would reintroduce this through a one-word edit
in a list, which is the same device used for `TERMINAL_STATUSES`. The boundary
is drawn no wider: a request merely awaiting approval holds no bytes that can
reach the chain, and blocking removal on those would make every pending review
an obstacle.

**Residual, stated rather than hidden:** a claim taken in the interval between
this check and the purge is still possible. Closing that needs a durable
generation fence revalidated immediately before the broadcast, which is the
same schema-level work 203401 waits on.

### 203449 — a flag that turned the review off

**high, fixed in `d2de786`.** `review --decision approve` mapped to
`no_confirm`, and `no_confirm` skipped `reviewer_approved` on both off-chain
paths. That is the component which starts on Reject and refuses Approve until
the end of the payload has been on screen. What remained was an OS prompt
naming a wallet and an operation — not evidence that anyone saw a permit, a
delegation, an order, or a login. A local process able to invoke the CLI could
queue a payload and reduce the owner's part to one authentication.

The flag is not the problem and is kept. The bypass is gone: neither reviewer
takes `no_confirm`, so there is no argument that can turn the review off.
Rejecting without a prompt is unchanged and must stay — it signs nothing, and a
scripted session must always be able to say no.

Scoped deliberately to the two payloads no policy can evaluate, where the
rendered bytes are the entire basis for the signature. `no_confirm` survives on
the transaction path, which is 203267 and remains known work.

The `--help` text promised the old behaviour, which is the fourth-shape detail
worth keeping: a caller reads the flag's description, not the function. It now
says approving a message or typed-data request still draws its review, and a

Removing a parameter means reverting the fix stops the tests compiling rather

### 203525 — a documented protection with no way to turn it on

**high, fixed in `ece9719`.** `docs/networks.md` calls `max_fee_per_gas` the
protection for automatic transactions, and it is right: their EIP-1559 fee
comes from an endpoint, no policy rule speaks about it, and nobody reviews it,
so `gas_limit × max_fee_per_gas` is what one dishonest answer can cost. Every
CLI surface that builds or edits a network omitted the field, and
`build_custom_network` hard-coded it to `None`. An operator following that
documentation through the supported CLI could not set it at all.

This is the third instance in this file's family, after 203385 and 201519 — a
ceiling silently removed by an edit, a ceiling omitted from the review, and now
a ceiling with no way to be set. Worth noting what they have in common: the
enforcement in `capped_fee` was correct the whole time.

It is now a flag, an override, an entry in the interactive form, and an
editable field with a validator, optional throughout. Blank clears it, because
an owner who set a ceiling has to be able to take it off without editing JSON,
and because the edit menu re-prompts with the current value — an unset ceiling
reads as blank and has to write back unchanged.

The comment justifying the omission argued that a fee ceiling is a judgement
about what the owner's transactions are worth rather than a property of the
chain. True — and so is `rpc_strategy`, which the form has always asked, as an
optional field, which is exactly the shape used here.

**What is worth recording is how it was caught.** Adding the field broke
`every_editable_field_round_trips_through_its_own_validator`, an existing test,
twice in a row: first for a missing reader arm, then for a missing validator
arm. Three functions had to agree about the field and the repository already
had that invariant under test. That is the shape of check this whole pass keeps
concluding is the durable one, written by someone else, working.

### 203685 — plaintext to anywhere

**high, fixed in `720343e`.** `validate_network` accepted `http` to any host.
An RPC connection carries the addresses, calldata, and balances this wallet
reads, and the fee estimate an automatic transaction is signed against — and
over plaintext to a remote host, anything on the path reads the first and
chooses the second, because `capped_fee` leaves an estimate unchanged when no
ceiling is configured and the shipped profiles configure none. That last clause
is 203525 and this one meeting: the finding is right that they share a
remediation.

Loopback stays allowed, because that is the case the allowance exists for — a
node on this machine, over a path with nothing on it. A LAN address is not
that; it is a network an attacker can be on, and it is refused with the rest.

**The placement is the whole judgement here.** `validate_network` is called by
`validate_config`, which runs on every `load`. A rule there would refuse to
load a configuration that already holds a plaintext endpoint — taking the
wallet roster and every other network with it, and leaving no way to run the
edit that would fix it. Failing closed is not always the safe direction: here
it would brick the wallet over a setting the owner may have chosen
deliberately. So the rule sits on admission — `network add`, `network edit`,
and an agent's network proposal — and an existing configuration keeps working
and can be repaired. That has a test of its own, beside the refusal and the
loopback allowance.

Worth being clear about what this does *not* address, since the finding leads
with it: an attacker who can rewrite `config.json` is not stopped by this, and
could point at their own `https` endpoint just as easily. What the rule
protects is an owner or an agent configuring plaintext without meaning to.

### 202891 — a hash agrees with whatever it was taken over

**high, fixed in `f11cd5c`.** `PendingRow::parse` checked that the stored bytes
hash to the stored hash. That establishes the two columns agree about the
bytes; it establishes nothing about the bytes being a transaction. Every reader
that does anything with an envelope decodes it — `signed_transaction_nonce` is
how reconciliation recovers the nonce — and that decode failing is the one
error `reconcile_all` swallows, deliberately, so a listing still renders.

A row with undecodable bytes therefore holds the single in-flight slot its
wallet and chain are allowed and can never leave it: reconciliation cannot
settle it, and `execute_automatic` reconciles the in-flight row before signing,
so nothing further can be signed there either. Only editing the database frees
it.

The parser now decodes, for the same reason and with the same effect as the two
checks immediately above it — whose comments already make this exact argument,
one step short. *"Refusing the row here turns a permanent wedge into a read
that fails loudly and names the request."*

**The fixtures had to become transactions**, and that is the part worth
recording. `ORIGINAL_BYTES` and the three cancellation constants were `0x0102`,
`0x0304`, `0x0506`, `0x0708`: bytes paired with their own keccak, satisfying
every check the parser made, and unreachable in production where the bytes are
always something this wallet signed. Eighty usages across one file, every one
of them asserting on data that could not exist. They are now real signed
EIP-1559 envelopes differing only in nonce, generated with the construction
`sign_prepared` uses.

That is the **sixth** fixture this pass found encoding the defect it sat beside,
after `fee_history_stub`, the median tests, `cancellation_reprices_…`,
`wrapping_prefers_a_space_…`, and `the_replay_set_forgets_the_oldest…`. The
pattern is consistent enough to state as a rule: **when a fixture can satisfy a
check that production data would satisfy for a different reason, the check is
weaker than it reads.** Every one of these six was a test built from the
minimum bytes that passed, rather than from the bytes the system actually
handles.

### 203562 — an estimate bounded from above and not below

**high, fixed in `4de7949`.** `sign_cancellation` checked the endpoint's
`estimate_gas` against the usable ceiling and nothing else. A cancellation is a
zero-value self-send whose intrinsic cost is exactly 21,000 gas, so an endpoint
answering `0` — or anything under half that, since the multiplier is 2 —
produced an envelope below the floor, which every honest peer rejects. Nothing
else checks it: a cancellation cannot be simulated, and this is the one signing
path that consults no policy.

The rejection is not the damage. The envelope is persisted before it is
broadcast, so each spends a slot in a history capped at
`MAX_CANCELLATION_ATTEMPTS`, and at the cap reconciliation stops repricing and
rebroadcasts the newest stored envelope. Eight bad estimates leave the owner
permanently unable to cancel, resending an invalid envelope forever while the
transaction they were trying to stop mines.

**Raised rather than refused**, which is the opposite of `capped_fee` and of
almost every other fix in this pass. `capped_fee`'s own comment gives the
reason: there, not signing is the safe answer; here, not producing an envelope
*is* the failure. Raising is exact rather than a guess — the floor is what the
chain charges, not a number chosen here — and `usable_gas_ceiling` has already
established the ceiling is at least the intrinsic cost, so the floor can never
breach it. There is a test for that, because "the fix cannot violate the bound
it sits under" is the kind of claim that is easy to assert and easy to get
wrong.

Extracted into `cancellation_gas_limit` rather than left as three chained
methods inside an async closure — fix-hierarchy item three, and the only thing
that makes the branch testable, since no fixture reaches it through a real
endpoint.

**First fix measured against the resource-bound rule**, and it passes on both
counts: the work happens before any human decision point, and the input is an
untrusted remote party's answer rather than a document the owner wrote.

### 203531 — a snapshot that decided where an envelope went

**high, fixed in `bae141e`.** `attempt_cancellation` re-read the pending record
and never read the configuration. The caller resolves the wallet and network
before the await; that snapshot then decides endpoint selection, chain-ID
validation, fee estimation, the gas ceiling, and where the envelope is
broadcast. Configuration writes replace the whole document atomically while
readers hold independent snapshots, so another CLI or the MCP server can
replace the profile — or remove the wallet — while this runs. It is the one
signing path with no policy and no review behind it.

The interesting part is that **the right fix here is not the fix for 203533**,
which is the same shape one command over. `transaction discard` refuses when a
profile *was* replaced, because a wrong answer there untracks a live envelope
and refusing costs the owner nothing. Applying that rule to cancellation would
be exactly the capability deletion the maintainer's review names: being unable
to cancel is the failure this path exists to prevent.

So this asks only whether the configuration changed *underneath the operation*,
not which profile is allowed, and the refusal points at running the command
again — which picks up whatever is current and succeeds. Same defect shape,
opposite remedy, decided by what a refusal costs.

Two mistakes of my own on the way, both the same one twice. The refusal test
matched across a string continuation, whose backslash survives
`split_whitespace` as its own token — the CRLF lesson in a second costume, so
the test strips continuations before comparing prose now. And the assertion
that this path does *not* call `network_for_record` was matching the
identifier, which the doc comment above it names deliberately to explain the
choice; it matches a call.

### 202491 — closed by `930b4f6`, with the residual stated

**high, no further change.** Filed separately from 203615 and it is the same
defect: the replay set was a `BTreeSet` evicted with `pop_first`, so eviction
was ordered by a number the peer chooses. A dapp could flood ids near
`u64::MAX` and have the *lowest* entry evicted — which is the legitimate id it
wanted to replay. `930b4f6` replaced it with a `HashSet` plus a `VecDeque` of
arrivals, so what is forgotten is the oldest thing to arrive.

**What that does not close, and cannot:** a bounded window is bounded. An
attacker who sends 4,096 messages after a request can still age it out and
replay it. That is true of any fixed-size replay set and is not fixable by
ordering.

**Why the residual does not matter here.** The party who could exploit it is
the dapp holding the session key, and a dapp that wants the same transaction
executed twice does not need to replay anything — it can send a second request
with a fresh id. The replay set is protocol-level de-duplication against a
relay that delivers a message more than once, not a semantic control over what
a session may ask for. What governs *that* is the policy the owner wrote, and
the automatic path is the authority they granted.

So the honest reading is: the ordering defect was real and is fixed; the
window's finiteness is a property, not a bug; and the finding's impact
paragraph describes something a malicious dapp can already do by asking twice.
Recorded rather than fixed, because the fix it implies — semantic replay
detection over plan contents — would refuse a dapp legitimately requesting the
same transfer twice, which is the capability-deletion shape the maintainer's
review warns about.

## The maintainer's review, and what changed because of it

`audits/v12-run-6304-overengineering-review.md` reviewed all 106 commits
against one test: *"the agent cannot do X" means "cannot do X without explicit
human approval."* The failure mode is a hard refusal standing in front of an
approval surface the product already builds. Verdict: not overengineered, one
genuine capability deletion, and two fixes that needed **more** work rather
than less. Four repairs followed.

**`7e73dfa` — the plaintext-RPC refusal (was `720343e`).** The one real
capability deletion. It fired before `confirm_network_change`, a live chain-ID
probe, and an OS authentication prompt — and the first of those prints the
complete RPC URLs. An operator with a node on Tailscale or a lab VLAN was told
no by a wall in front of the screen that exists to let them say "yes, I know".

A flag could not fix it: `add_configured_network` and
`replace_configured_network` are crossed by the agent's proposal and its
acceptance, so a boolean threaded through them is one the agent can set.
`InteractiveOwner` can only be minted from an `InteractiveProof`, whose sole
production origin is `from_terminal` and whose call sites `tests/boundary.rs`
enumerates individually — `put_network_proposal` cannot construct one, so an
agent still cannot propose plaintext at all. The type says *which path the
write came down*, not that the owner agreed; agreement is the confirmation
screen returning true, and that screen now warns about the URL by name,
derived from the strings it is about to print so the two cannot diverge.

The boundary test caught the new origin, which is what it is for.

**`1f50e74` — the wallet-removal refusal (was `f6429a9`).** Same shape, milder.
The in-flight list is a set of warnings on the approval now rather than a wall
in front of it. An owner whose node is gone and whose transaction will never
mine is entitled to remove the wallet; refusing left them editing the database,
which is the outcome the rest of that file works to avoid.

**`77e9103` — the zero-address refusal (was `7c72cd3`).** The opposite problem.
It sat on `transfer_plan`, which only `wallet_send_transfers` reaches;
`wallet_send_execution_plan` reaches the same send with a producer-authored
plan and `ExecutionPlan::validate` never looked at the recipient. **One of this
pass's own fixes reintroducing theme four.** Moved onto the plan. The rationale
narrowed with it: I had written "a great many ERC-20s burn the amount", and
OpenZeppelin and most implementations revert — native value is the destructive
case and carries the check alone. The ERC-20 leg is consequently no longer
covered, deliberately, and the test says so.

**`b380f93` — the install verification (was `01d13cb`).** Incomplete. `README.md`
and `docs/installation.md` still piped an unverified script from `main`, which
is worse than what the fix replaced because no signature covers a branch. The
project was paying for a cosign-mandatory install in its documentation while
keeping the unverified path as the default.

Two notes in the review were deliberately **not** acted on. The triple rule
validation in `856a333` and the decode-per-read in `f11cd5c` are both named as
trade-offs rather than defects; spending commits there is the overengineering
the review is warning about.

## The standing rule for resource bounds

The review's largest point is forward-looking, and it is adopted here as the
rule for the remaining mediums:

> Fix a resource bound only where the work happens **before a human decision
> point** and **on behalf of an untrusted remote party** — RPC responses, dapp
> payloads, WalletConnect sessions. Where the input is a document the owner
> wrote or approved, record the finding as `accepted` and move on.

About forty of the 192 mediums restate "a limit applied after the work it was
meant to prevent", and `35ed495` is the first fix of that shape: four
constants, a new tree walk, ~50 production lines and 84 test lines, to bound a
document the owner authors and approves, on a single-user local process, where
`serde_json` already caps depth at 128. Defensible once. Forty times it is a
second validation layer across the kernel with its own constants, tests, and
maintenance — defending the owner's machine against the owner's own document.

`35ed495` predates the rule and stands; it is not worth reverting. Everything
after it is measured against the rule.

## A note on source-scanning tests

Several fixes here are pinned by reading the source rather than by exercising
the behaviour, because what went wrong was a property no fixture can hold still
— a build-time race (203661), a relay race (203729), the ordering of a check
inside a function (203435, 201700), a visibility (200607). The repository
already uses that technique in `tests/boundary.rs`, and it is the right one for
these. It has a failure mode worth writing down.

`201700`'s wiring test searched for `"let stored = policies.put(\n"`. The
checkout is CRLF on Windows, so the newline in the needle matched nothing,
`split_once` returned `None`, and the test panicked — **in CI only**. It passed
on every local run. A source-scanning test that cannot find its needle does not
report "the property is gone"; it reports whatever the surrounding code does
with `None`, which is a different and much less legible failure.

Two rules came out of it, and every other such test here was checked against
both: **no newline in a needle**, and **no byte-distance assertion that a line
ending could push over its bound**. `str::lines()` is safe and is what the
`203661` test uses.

Caught by CI at `806b5d2`, fixed in `1054fe1`. Worth noting the sequence: this is
the one thing in the pass the local gate could not have found, and it was found
by the platform the local gate cannot run.

## A note on the gate

`cargo test --workspace` cannot complete unattended on macOS:
`tests/credential_store_startup.rs` runs the real CLI, which blocks on a
Keychain prompt and hangs indefinitely (observed at 0% CPU for 18 minutes on
clean `main`, before any change here). Everything above was gated with

```sh
cargo fmt
cargo clippy --workspace --all-targets      # clean
cargo test --workspace --lib --bins \
  --test boundary --test example_policies \
  --test local_reference --test shipped_assets   # 909 passed, 0 failed
```

CI runs the excluded test on Linux, where the credential store does not prompt.
Worth marking it `#[ignore]` locally or gating it on an environment variable so
the documented gate actually terminates on a developer machine.
