# Security model

- This is one local stdio MCP process. It parses, simulates, policy-checks, signs, validates, persists, and broadcasts structured execution plans.
- Private keys are created or imported only by the separate human CLI and remain in the OS credential store, in per-wallet entries separate from the encrypted database and its key, so a copy of the data directory carries no key material. No MCP input or output carries a private key, mnemonic, password, arbitrary digest, or generic signing request.
- Key entries carry no biometric or presence requirement, deliberately: this wallet is built for unattended agent operation, and a key the OS would not release without a live human could not sign automatically at all. For the automatic path the active policy is therefore the security boundary, not key custody — whatever the policy permits is reachable without a further gate, so treat the policy, and what the wallet holds, as the limit of what an agent can do. Owner authentication covers the moments key material is used or destroyed — the exceptional review path, key export, and wallet removal — and one more: replacing a wallet's policy, whether from a file, a preset, or an agent proposal. The policy is the boundary itself, so rewriting it is authenticated like signing even though it reads no key material. Other configuration changes grant no signing authority and are confirmed in the user's terminal instead.
- Current policies and pending transaction lifecycle rows share one SQLCipher database. The database key is a distinct 256-bit OS-credential-store secret. There are no daily limits, spend counters, allowance reservations, or rollback-sensitive consumption records.
- Simulation sends the exact target, value, calldata, and any EIP-7702 delegation override to eth_simulateV1 at a pinned parent block. There is no local EVM, eth_getProof, or eth_call fallback for signing decisions. The configured RPC executes the EVM and remains a trust dependency for state accuracy.
- Execution plans, read-call bundles, and token lists may be supplied by reference: the wallet fetches the body from a public https URL the caller names. These are the only outbound requests that are not a configured chain RPC. Admission is narrow — https on the default port; no credentials, fragments, or redirects; no private, loopback, link-local, or otherwise reserved addresses, checked against every resolved address and pinned for the connection; and a 16 MiB response cap. Fetched bytes are verified against the caller-supplied keccak256 digest when present, then parsed and validated exactly like inline input, and error paths never echo response bytes. A data: URI is decoded locally and touches no network. A read-call bundle parses into exactly the batch-read argument surface and nothing more — unknown fields are rejected, so a fetched bundle cannot smuggle a fork id or a further reference — and its chain_id must equal the one the tool call itself selected, so a reference never redirects a read to a chain the caller did not name. A token list is parsed leniently by comparison — published lists disagree about field spelling and chain-ID notation, and a wallet that refused them would push the owner toward hand-editing the file, which is the one step that turns a curator's claim into an agent's. That is safe because a list authorizes nothing: it yields display-name suggestions the owner still confirms in the CLI, entries this wallet cannot represent are dropped rather than coerced, and `wallet_get_balances` reads only the addresses. Referencing a list changes who carries the bytes, never who decides what they mean.
- Temporary simulation forks are an agent workflow tool held only in this process's memory. A fork is an ordered list of already-validated plans plus one pinned parent block; every call replays that list as consecutive eth_simulateV1 blocks, so the RPC still executes everything and no simulated state is stored or reconstructed locally. A fork cannot create a pending request, produce signed bytes, mark anything approved, or satisfy a policy rule, and its policy findings are advisory; submission always re-simulates and re-policy-checks against real chain state, so 'it passed on the fork' never substitutes for that. Forks have no CLI surface and are never shown at approval time, so a human is never asked to read agent-supplied hypotheticals while deciding whether to sign. They expire, are capped per wallet and per plan, and do not survive a restart.
- Automatic transactions persist their exact signed envelope and hash before first submission. Approval and crash-recovery retries never re-sign or alter that transaction.
- Owner-requested cancellation is the one signing path that consults no policy. Its envelope shape is fixed and constructed only from the stored record and the chain — a 0-value self-send with empty calldata and no authorization list, at the exact nonce of an envelope this wallet already signed and submitted — so like an exact-byte rebroadcast it cannot expand what was authorized, only consume the in-flight nonce at the cost of gas. Fees derive from the incumbent envelopes and the current market estimate with a bounded bump, never from caller input; the exact cancellation bytes are persisted before submission; and the record resolves only by receipts, to cancelled, confirmed/reverted, or replaced, whichever the chain settles.
- Policy exceptions require separate terminal review plus OS-backed owner authentication. Their review digest binds the exact plan, nonce, gas, fees, call, and delegation; signing performs no RPC lookup after authentication. The MCP server can wait for or observe that decision but cannot approve it.
- wallet_propose_network writes nothing. It settles every local field and naming conflict, admits the endpoint (public https, no credentials, no private or reserved address), and queues the profile for `ekubo-wallet network review`, where the owner confirms it in the terminal and authenticates against the OS before the chain ID is verified and the profile stored. There is no MCP configuration mutation: policy, network, custody, token, address-book, and approval writes are all CLI-only, and every one of them takes both a terminal confirmation and an OS presence check.
- The token database is display data used for listings and portfolio reads, stored inside the authenticated encrypted database so it cannot be edited outside this process to misrepresent balances. MCP tools may add to it only through on-chain Multicall3 verification, a chain_id/address pair is never overwritten, and no signing or policy decision reads it.
- The address book maps per-chain aliases to addresses inside the encrypted database, so an alias cannot be retargeted by editing a file. Only the human CLI can mutate it, after a confirmation in the user's terminal. Nothing in the signing or policy path reads it, and an alias never substitutes for reviewing the actual address.
- Agents may propose a replacement policy with wallet_propose_policy. A proposal is inert data in the encrypted database: one per wallet, bound to the exact policy revision it was written against, replaced by any newer proposal, and applied only by the human CLI after presenting a minimized permission diff plus the agent's rationale, confirming it in the terminal, and OS-backed owner authentication.
- EIP-712 typed-data requests always queue in the encrypted database for separate human CLI review, which displays the complete payload, requires terminal approval plus OS owner authentication, and only then signs. The MCP server can create and observe typed-data requests but cannot approve or sign them. No policy is consulted for a signature, including a recognized permit: a permit is consumed once, so a rule permitting one under a limit permits an unbounded series of them under that same limit, and the wallet holds no counters to notice.
- No MCP tool other than wallet_get_legal is reachable until the user has accepted the current Terms of Service and Privacy Policy through the interactive CLI; the signing paths repeat the check as defense in depth. Acceptance binds the exact document digests; changed documents fail closed until re-accepted.
